# 06 — Симуляция: юниты, навигация, бюджеты

Целевой масштаб — 5000+ юнитов одновременно. Это меняет почти все решения
по сравнению с «обычной» RTS на 200 юнитов, поэтому масштаб зафиксирован
здесь как требование, а не как пожелание.

## Бюджеты производительности

Всё, что ниже, — пороги бенчмарков в CI. Регрессия проваливает сборку.

| Что | Бюджет | Комментарий |
|---|---|---|
| Тик симуляции при 5000 юнитах | **≤ 10 мс** | при частоте 30 Гц бюджет 33.3 мс, берём запас ×3. **Но сама частота под вопросом — OQ-16** |
| Полный мешинг чанка | **≤ 350 мкс** | реальная цифра из README крейта, см. `05-voxel-world.md` |
| Ремешинг при устойчивой копке, на кадр | **≤ 5 мс** | амортизировано, очередь чанков |
| Обновление навигации при устойчивой копке, на тик | **≤ 3 мс** | батч изменений за тик, пересчёт затронутых секторов |
| Правки вокселей на тик | `MAX_VOXEL_EDITS_PER_TICK` | потолок **в мировых единицах объёма**, не в штуках, с очередью на переполнении (ADR-013) |
| Разрешение попаданий при 5000 юнитах, на тик | **≤ 2 мс** | луч по вокселям тома вместо вычитания числа — самое дорогое следствие ADR-016 |
| Обновление сети энергии, на тик | бюджет **не определён** | появился с ADR-022, померить на этапе 0 |
| Кадр рендера при обзоре RTS | **≥ 60 FPS** | 2560×1440, RTX 5090 |

**Частота тика 30 Гц — не проверенное решение, а умолчание.** Supreme
Commander, наш явный ориентир по масштабу, тикал симуляцию на **10 Гц**, то
есть имел 100 мс на тик вместо наших 33, и интерполировал в пользовательском
слое на 60 fps. У нас работы на тик заметно больше (правки вокселей, обновление
навигации по меняющемуся миру, разрешение попаданий по вокселям), а бюджета
втрое меньше. Это OQ-16.

Два условия, без которых цифры бессмысленны:

- **Все замеры записываются вместе с числом доступных потоков.** На этой машине
  ОС видит 8 ядер из 16 (`01-concept.md`, R6). Публикуемые в статьях цифры
  обычно с 32 потоков — сравнивать напрямую нельзя.
- **Замер до геймплея.** Бюджеты меряются на скелете на этапе 0
  (`09-roadmap.md`), а не после того, как всё написано. Если 5000 юнитов не
  укладываются на скелете — режется масштаб, пока не поздно.
- **Нагрузка устойчивая, а не событийная.** Копка это экономика (ADR-013),
  поэтому мерить надо «N юнитов копают M тиков подряд», а не «один взрыв».
  Это разные режимы, и первый гораздо жёстче.

## Хранение юнитов

Плотные SoA-массивы, generational id (ADR-009):

```
positions:  Vec<FxVec3>     // параллельные массивы, индекс = слот юнита
velocities: Vec<FxVec3>
orientation:Vec<FxQuat>     // том юнита ориентирован в мире
volume:     Vec<VolumeRef>  // ссылка на шаблон типа либо на собственную копию
core_ok:    BitVec          // ядро цело; скалярного HP нет (ADR-016)
kind:       Vec<UnitKindId> // индекс в таблице типов из данных
owner:      Vec<PlayerId>
generation: Vec<u32>        // защита от висячих ссылок на переиспользованный слот
```

`VolumeRef` — copy-on-write: неповреждённые юниты одного типа указывают на
общий шаблонный том, собственную копию получают при первом повреждении.
Один байт на воксель, палитра материалов.

Обход — по индексу, всегда в одном порядке. Это и есть гарантия из правила 3
в `04-determinism.md`, полученная бесплатно.

Пространственные запросы («кто рядом») — равномерная сетка / spatial hash по
тем же индексам. Quadtree не нужен: юниты одного порядка размера.

## Навигация

Три уровня, как в Supreme Commander 2 и StarCraft 2.

**Уровень 0 — граф проходимых вокселей (ADR-014).** Копка порождает шахты,
туннели и несколько проходимых уровней в одной колонке, поэтому heightmap не
годится. Узел графа — твёрдый воксель, над которым есть воздух; классификация
Walkable / Climbable / Obstructed. Это 2-мерное многообразие, вложенное в 3D:
память растёт как площадь поверхности, а не как объём.

**Уровень 1 — cost field** поверх этого графа, на сетке **грубее воксельной**.
Грубость принципиальна: снятие одного воксела не должно менять граф, иначе
непрерывная копка будет непрерывно инвалидировать навигацию. Изменения
батчатся за тик и применяются одним пакетом в фазе `nav_update`; затронутый
сектор пересчитывается целиком, а не инкрементально по ячейке — дороже на
событие, зато предсказуемо и детерминированно.

**Уровень 2 — граф порталов.** Карта режется на сектора, между соседними
секторами — порталы. Дальнее планирование = A* по графу порталов, а не по
тайлам. Плюс идентификаторы связных компонент («островов»): если старт и цель
в разных компонентах, путь невозможен, и это выясняется за одно сравнение,
а не за полный обход карты. На разрушаемом рельефе компоненты сливаются и
разделяются — прокопали проход, два острова стали одним.

**Уровень 3 — flow field.** Для каждой активной цели строится поле направлений
через integration field (решение уравнения эйконала на секторе). Юниты не
ищут путь — они читают направление из поля. Один расчёт обслуживает всю группу,
что и делает 5000 юнитов возможными.

Схема решателя — **итерационная (FIM) в форме Якоби с двойной буферизацией**, а
не fast sweeping: Якоби порядок-независим по построению, то есть детерминирован
без дополнительных приёмов, а sweeping плохо сходится именно на картах с
барьерами — то есть на прокопанной карте (`18-gpu-compute.md`, 12.1).

**Три рычага из Supreme Commander 2, которые надо заложить сразу:**

1. **Глобальный статический «чистый» cost field.** Свободный сектор ссылается
   на один общий массив вместо собственного. В SupCom 2 так было помечено
   **50–70% проходимого пространства** — эта память и это интегрирование не
   тратятся вообще.
2. **Кэш полей с ключом по порталу, а не по цели** — работа переиспользуется
   между разными запросами.
3. **Приоритетная очередь с бюджетом в миллисекундах на элемент**, а не «всё
   грязное за тик».

Раскладка бит оттуда же: cost field 8 бит на клетку, integration field 24 бита
(16 стоимости плюс 8 флагов), flow field 8 бит.

Сверху — локальное избегание, чтобы юниты текли, а не толкались. Это
единственное место, где юнит смотрит на соседей.

**Начинать с boids-разделения, а не с ORCA — и это решение по цифрам, а не по
вкусу.** Из опубликованного замера GPU-реализации ORCA (Charlton и соавторы,
CGI 2019, GTX 970) выводится, что на CPU ORCA стоит около **2 микросекунд на
агента**, то есть при 5000 агентах порядка **10 мс на i7-4790K и 3–5 мс на
нашей машине**. Это **треть-половина всего бюджета тика в 10 мс** и самая
дорогая вещь на агента во всём тике.

Разделение boids — это O(соседей) без линейного программирования, дешевле на
порядок, тривиально векторизуется в `Fx` и не требует решателя. А ORCA пришлось
бы ещё и переписывать в fixed-point ради детерминизма, и LP в фиксированной
точке — отдельная неприятная работа с вырожденными случаями.

ORCA — только если разделение выглядит плохо, и с обязательным замером цены.
Третий вариант, если поведение толпы окажется центральным: Continuum Crowds,
где стоимость зависит от карты, а не от числа агентов, и который естественно
сливается с уровнем 3, потому что это то же уравнение эйконала с добавкой
плотности к полю стоимости.

Готового крейта нет и не будет: `bevy_northstar` умеет HPA*/A*/Theta*, но не
flow field, отстаёт от Bevy на релиз и не рассчитан на постоянно меняющуюся
геометрию. Пишем сами (ADR-007).

## Бой

Поиск целей — через spatial hash, не полным перебором. Урон, дальность,
перезарядка — из данных. Линия огня учитывает воксельную геометрию: холм
закрывает, и это меняется, когда холм срыли. Проверка линии — воксельный
raycast по DDA, дешёвый; частота проверок ограничена (не каждый юнит каждый тик).

**Разрешение попадания — единственное место, где нужна воксельная точность**
(ADR-016). Луч идёт по тому юнита: снимает воксели брони, экранирование
работает геометрически, юнит выходит из строя при разрушении ядра. Скалярного
HP нет. Связность отстреленных частей с ядром проверяется по накоплению
повреждений, а не на каждое попадание.

**Столкновения и движение — упрощённый прокси** (цилиндр или бокс из габаритов
тома). Воксель против воксела на 5000 юнитов не выживет, и там это не видно.

**Смерть юнита → обломок**: воксельный том из тех же материалов, реклеймится
тем же кодом, что копка (ADR-017). Добивание снижает выход.

## Туман войны

**Это две разные сущности, и их надо разделить.**

**Симуляции** нужна грубая битовая сетка: от неё зависит, что видит AI, значит
она обязана быть детерминированной. Считается на CPU дёшево — 5000 юнитов,
штамп предрассчитанного диска, `OR` по битам.

**Рендеру** нужна мягкая маска высокого разрешения. Она неавторитетна, живёт на
GPU и может считаться как угодно.

Смешивать их в одну сущность — ошибка: первая обязана быть детерминированной и
грубой, вторая свободна и должна быть гладкой.

## Экономика

Все числа — в `data/*.ron`: стоимость, время постройки, скорость добычи, HP,
урон. Ни одного балансного числа в исходнике (`CLAUDE.md`, инвариант «данные,
не код»). Это одновременно правильный дизайн и то, что делает баланс
доступным модам без единой строчки кода.

Ресурсов два и они разной природы (ADR-021, ADR-022): материя — сохраняющийся
физический запас в контейнерах, энергия — несохраняющийся поток от разрушения
материи. OQ-3 закрыт.

## AI противника

Три слоя, по возрастанию сложности; первая версия — только первые два:

1. **Build order** — скриптовая последовательность из данных. Достаточно
   для играбельного среза.
2. **Стратегический выбор** — utility AI: набор конкурирующих действий с
   оценками. Хорошо ложится на RTS, где вариантов много и они несравнимы.
3. **Тактика** — steering и позиционирование поверх flow field.

GOAP и полноценное планирование — оверкилл на старте.

AI работает **внутри симуляции** и через тот же интерфейс команд, что игрок.
Это не стилистика: иначе AI не будет детерминированным, а реплеи с ботами
перестанут воспроизводиться. И это же делает AI моддируемым бесплатно.

## Что режется первым, если бюджет не сходится

По порядку, от дешёвого к болезненному:

1. Частота проверки линии огня и поиска целей (амортизация по тикам).
2. Разрешение навигационной сетки.
3. `MAX_DYNAMIC_BODIES` — меньше одновременных обломков.
4. Число юнитов: 5000 → 3000.
5. И только потом — архитектура.

Порядок важен: он записан здесь, чтобы под давлением дедлайна не начали
резать с конца.
