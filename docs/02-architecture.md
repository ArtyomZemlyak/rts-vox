# 02 — Архитектура

## Принцип

Один поток данных, одна граница, никаких обратных стрелок:

```
   сид + набор модов + поток команд
                |
                v
        +---------------+
        |   sim-core    |   fixed-point, детерминировано, headless
        |  (SoA, tick)  |   ничего не знает про рендер
        +---------------+
                |
                | состояние + дельты (read-only)
                v
        +---------------+
        |    render     |   Bevy 0.19, float, свободно
        |  (Bevy ECS)   |   никогда не пишет в sim-core
        +---------------+
```

Рендер читает. Ввод игрока не меняет состояние напрямую — он превращается в
**команду**, команда попадает в очередь на тик N+delay, и только симуляция
её применяет. Это и есть lockstep-модель; в одиночной игре delay = 0, но путь
тот же, и потому сетевой код позже не потребует переписывания геймплея.

## Крейты

```
rts-vox/
├─ crates/
│  ├─ fx/            fixed-point Q32.32: арифметика, векторы, sqrt, тригонометрия
│  ├─ voxel/         сетка, чанки, палитра, маски занятости, разрушение,
│  │                 **связность** (отделение кусков и связность пустот)   → fx
│  ├─ worldgen/      генерация. Чистая функция от сида                    → fx, voxel
│  ├─ nav/           cost field, flow field, порталы                      → fx, voxel
│  ├─ modding/       загрузка RON, Luau-хост, детерминированные биндинги  → fx
│  ├─ sim-core/      мир, юниты, приказы, тик                → fx, voxel, worldgen, nav, modding
│  ├─ sim-cli/       headless-прогон, дампы, реплеи, хеши    → sim-core
│  ├─ meshing/       чанк → квады. Рендер-слой, но без Bevy  → voxel
│  └─ render/        Bevy-приложение. Единственный крейт, который знает про Bevy
├─ data/             ванильный контент в RON — грузится тем же путём, что моды
├─ mods/             моды (в разработке; ванильный контент лежит в data/)
├─ tests/            интеграционные: реплеи, бот-против-бота, golden-карты
└─ docs/
```

Правило зависимостей, проверяемое механически: **ни один крейт кроме `render`
не имеет `bevy`, `wgpu` или `winit` в `Cargo.toml`.** Это условие на CI, а не
пожелание. Проверка именно по трём именам, а не по одному `bevy`: рендерная
зависимость просачивается через `wgpu` так же легко.

**`meshing` принадлежит рендер-слою**, хотя и не зависит от Bevy. Мешинг — не
симуляция: его результат не входит в хеш состояния, и потому лестница ADR-011
разрешает перенести его в WGSL. Из этого следует, что запрет на float на него
**не распространяется** (`03-determinism.md`). Он остаётся отдельным крейтом
только потому, что делит с `voxel` маски занятости.

**Маски занятости — состояние симуляции, а не приём мешинга.** Поколоночные
u64-маски читают четыре потребителя: мешинг и пропуск пустоты в рендере,
DDA-луч разрешения попаданий и коллизии в симуляции. Владеет ими крейт
`voxel`; GPU-копия производна, неавторитетна и хранится как две u32 (в Vulkan
`countLeadingZeros` и `firstTrailingBit` только 32-битные, naga #5276).

## Контракт sim-core ↔ render

Узкий намеренно — чтобы замена рендера (ADR-002, триггер пересмотра) стоила
дни, а не месяцы.

```rust
// sim-core отдаёт наружу
fn tick(&mut self, commands: &[Command]);
fn state_hash(&self) -> u64;

// мир
fn voxel_delta(&self) -> &[ChunkChange];   // какие чанки изменились с прошлого тика
fn voxels(&self, chunk: ChunkId) -> ChunkView<'_>;

// тела: юниты, постройки, обломки, отделившиеся куски
// BodyId и VolumeId несут поколение — как UnitId. Отложенная правка может
// пережить свою цель, и висячая ссылка тут означает начисление в никуда.
fn bodies(&self) -> BodiesView<'_>;        // SoA: трансформ, масштаб, состав, владелец
fn volume(&self, v: VolumeId) -> VolumeView<'_>;  // палитровый индекс + палитра
fn body_parts(&self, b: BodyId) -> &[PartRef];    // составные тела (ADR-020)

// экономика
fn containers(&self) -> ContainersView<'_>;// вместимость и содержимое по материалам

// события и состояние
fn events(&self) -> &[SimEvent];           // взрывы, смерти, завершение постройки
fn snapshot(&self) -> Snapshot;            // ключевой кадр для позднего входа
fn restore(&mut self, s: &Snapshot);
```

Что изменилось относительно первой версии контракта: добавлены тела с
трансформами и масштабным множителем (ADR-005, ADR-019), воксельные тома как
самостоятельный класс данных для марша луча (ADR-018), иерархия составных тел
(ADR-020), контейнеры (ADR-021) и снапшот. Рендер по ADR-018 обязан получать
**тома, боксы и трансформы**, а не только чанки мира.

Три вещи, которые этот контракт фиксирует:

**Рендер получает воксели, а не меши.** Мешинг — задача рендер-слоя, не
симуляции. Симуляция знает, какие воксели изменились; как это показать —
не её дело. Именно это позволяет заменить полигональный путь на ray-marching
(ADR-006), не трогая ядро.

**Дельты, а не полное состояние.** При разрушаемом мире полный дамп мира
каждый кадр невозможен. `voxel_delta` — список изменившихся чанков за тик,
рендер ремешит только их.

**События, а не поллинг.** Взрыв, попадание, смерть — это `SimEvent`, из
которого рендер порождает unsynced-эффекты (ADR-005). Симуляция при этом
про эффекты ничего не знает.

[QUESTION Q-42 blocks:stage-2 by:tech]
Отдаёт ли `sim-core` рендеру **поток команд правок** (регион, операция,
материал) вместо уведомления «этот чанк изменился»? Замер говорит за поток:
вытягивание изменившихся чанков стоит 192.8 мс копирования против 15 мс самой
правки. Но проигрываемый журнал означает, что рендер держит **собственную
производную копию мира** — ровно та проблема двух расходящихся представлений,
ради избегания которой ADR-020 запретил меши в симуляции. Если брать поток,
то с явным правилом «копия рендера производна и пересинхронизируется из
`voxels()`». Требование «все правки тика идут одним проходом» при этом
рендерное ограничение диктует симуляции, как батчить, — это тоже часть
вопроса.

[QUESTION Q-43 blocks:stage-6 by:human]
В контракте нет канала для **энергетических объектов**. ADR-022 называет
гладкий визуал энергии третьим путём рендера, но рендеру неоткуда взять
«число и трансформ» щита: в контракте есть тела, тома, контейнеры и события,
энергии нет. Связан с Q-34 в `07-economy.md`.

**Снапшот — часть контракта, а не «потом».** Поздний вход и переподключение в
lockstep требуют передать состояние мира, а полный воксельный мир — гигабайты
(`04-world.md`, `analysis/05-mining-and-terrain.md`). Значит формат ключевого
кадра проектируется сериализуемым с первого дня, а не добавляется поверх.

Готовые уроки по устройству снапшота, из шипнутого rollback-движка
(NetherRealm, Mortal Kombat / Injustice 2): кольцевой буфер по размеру окна;
**сохранять только изменяемые данные**; не дельта-кодировать; сериализацию
можно параллелить (у них 2.7 мс → 1.3 мс при вдвое большем объёме), а вот
пост-обработку после восстановления они намеренно оставили однопоточной.
И главная их оптимизация: **сохранять только подтверждённый кадр**, а не все
кадры окна — хуже средний случай, заметно лучше худший.

## Тик

**Фиксированная частота 30 Гц** (ADR-027). Порядок фаз — явный список, а не
расписание фреймворка (ADR-009), и он фиксирован навсегда: его изменение
меняет хеши всех golden-файлов.

Список **окончательный** (ADR-048): фазы, чьи подсистемы реализуются на
этапе 6+, существуют пустыми заглушками и участвуют в хеше. Зарезервировать
фазу сейчас стоит ноль, дописать после первого golden-файла — перегенерация
всего.

```
 1. apply_commands      команды игроков и AI из очереди этого тика
 2. mod_pre_tick        synced-скрипты модов, фаза «до»
 3. voxel_edits         дренаж очереди правок: копка, реклейм, бой, затопление
 4. destruction         связность породы, отделение кусков, схлопывание,
                        связность повреждённых частей юнитов
 5. fluids              уровни водоёмов, связность пустот (ADR-042)
 6. bodies              падение тел, широкая фаза, раздавливание (ADR-036/037)
 7. nav_update          проходимость немедленно, интегрирование по очереди
 8. movement            flow field + локальное избегание
 9. combat              цели, попадания по вокселям, щиты (ADR-040)
10. logistics           переливы между контейнерами, снабжение заводов (ADR-021)
11. economy             производство, постройка, энергетический баланс (ADR-022)
12. visibility          туман; обновление памяти игроков о мире (ADR-029)
13. mod_post_tick       synced-скрипты модов, фаза «после»
14. cleanup             мёртвые, запекание, таймеры распада, снятие резервов
15. hash                контрольная сумма состояния (только в debug/тестах)
```

Копка не разделена между `economy` и `destruction`: она целиком в
`voxel_edits`, а зачисление добытого — в `logistics`. Так одна операция не
размазана по двум фазам.

`fluids` после `destruction`: затопление зависит от того, соединился ли прокоп
с водоёмом, а это связность. `bodies` до `nav_update`: раздавленное перестаёт
быть препятствием в тот же тик.

**`visibility` идёт после `nav_update`, значит навигация работает с памятью
игрока за прошлый тик.** Это осознанно и записано здесь, чтобы не было
переоткрыто как баг и не «починено» перестановкой фаз — перестановка
перегенерирует все golden-файлы.

`destruction` строго до `nav_update`, а `nav_update` строго до `movement` —
иначе юниты в течение тика идут по несуществующей геометрии. Это тот класс
багов, который в недетерминированной системе ловится месяцами, а здесь падает
как расхождение хеша.

Рендер идёт своей частотой и интерполирует между тиками; интерполяция живёт
только в рендере. **Целевая частота — 60 FPS** (`10-budgets.md`): при 144 Гц
кадр это 6.9 мс, и бюджет в 5 мс на ремешинг в него не влезает вместе со всем
остальным. 144 Гц — не цель проекта.

## Как это проверяется без человека

`sim-cli` — интерфейс агента к игре:

```bash
# прогнать N тиков и напечатать хеш состояния
cargo run -p sim-cli -- --seed 42 --ticks 1000 --dump-hash

# ASCII-карта проходимости и позиций юнитов: дешёвые «глаза» агента
cargo run -p sim-cli -- --seed 42 --ticks 300 --dump-ascii

# воспроизвести записанный реплей и сравнить с эталоном
cargo run -p sim-cli -- --replay tests/replays/dig-through-ridge.rpl --verify

# два бота на 10k тиков: проверка, что игра сходится и не десинкается
cargo run -p sim-cli -- --seed 7 --bots 2 --ticks 10000 --report
```

Скриншоты — через `bevy_brp_mcp` в рендер-слое, но это **дополнение**, а не
основной канал. Если проверка подсистемы требует скриншота — подсистема
спроектирована неправильно.

## Структура данных мира

Три уровня, каждый со своей ответственностью:

**Статическая воксельная сетка.** Размеры чанков **разные у разных подсистем**
и это нормально (ADR-024): хранение — 32³ row-packed с горячим и холодным
слоями; мешинг — 62³ полезных плюс паддинг соседей, чего требует
`binary-greedy-meshing`; навигация — своя, более грубая сетка. Хранилище отдаёт
срезы, а не диктует размер всем. Палитровое кодирование материалов, RLE на
диске.

**Тела.** Юниты, постройки, обломки и отделившиеся куски — всё это воксельные
тома со своим трансформом и масштабом, модель Teardown («тысячи небольших
томов, заполненных вокселями»). Их число ограничено, осевшие постройки
запекаются обратно в статическую сетку с конверсией масштаба (ADR-005,
ADR-019, ADR-023). Детали и бюджеты — `04-world.md`, `05-units.md`, `10-budgets.md`.

**Навигационные слои.** Уровень 0 — граф проходимых вокселей (ADR-014):
именно он, а не heightmap, переживает туннели и нависания. Поверх — cost field
и flow field на более грубой сетке. Пересчитываются локально по `ChunkChange`;
что обязано обновиться в тот же тик, а что может отставать —
`06-navigation.md`.

## Что здесь намеренно не описано

Сеть, звук, UI. Всё это добавляется поверх контракта и его не меняет.
Сериализация из этого списка **изъята**: снапшот входит в контракт (см. выше),
потому что поздний вход в lockstep без него невозможен. Если окажется, что меняет — это ошибка контракта, и её
надо чинить здесь, а не обходить на месте.
