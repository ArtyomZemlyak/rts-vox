# Быстрый цикл проверки настоящей симуляции

Для изолированного контракта UI-анимаций используется компактный набор
`python scripts/test-fast.py --suite ui-animation`: ui_motion, optical_ui
и production_hud. Он проверяет реальную ECS с фиксированным Time,
текст/области клика и реальные production_exit без GPU и ожидания wall-clock.

Рабочий путь для изменений движения, экономики и ИИ. Инструменты не создают окно,
не используют GPU и не меняют физику или частоту тиков. Симуляция выполняет обычные
тики как можно быстрее, без ожидания реального времени.

## Проверки по изменённой системе

```powershell
python scripts/test-fast.py --suite smoke
python scripts/test-fast.py --suite movement
python scripts/test-fast.py --suite movement-quick --reuse-passed
python scripts/test-fast.py --suite movement-quick --suite smoke --reuse-passed
python scripts/test-fast.py --suite ai
python scripts/test-fast.py --suite scenes

# Каждый фильтр обязан найти хотя бы один существующий тест.
python scripts/test-fast.py --package sim-core --filter height_tests:: --filter tracked_motion_tests::

# Без повторной сборки, только если fingerprint исходников/настроек и SHA binary совпадают.
python scripts/test-fast.py --suite movement --no-build

# Посмотреть точный список без выполнения.
python scripts/test-fast.py --suite movement --list
```

Есть PowerShell-обёртка `scripts/test-fast.ps1` с теми же аргументами.
`--suite` можно повторять: фильтры объединяются по пакету/target, каждый target
собирается и перечисляется один раз, каждый выбранный тест исполняется один раз.
Без явного набора используется `smoke`. Одновременно выбирать набор и custom
`--package/--filter` нельзя: запускатель не игнорирует одну из этих настроек.
`movement-quick` — короткая проверка походки, начала движения, лесного склона,
малых ступеней, появляющегося кратера, низкоуровневого восстановления опоры и
опорной сетки. На срезе 589 это **22 SIM + 6 nav**. Он не заменяет полный
`movement`, особенно при изменении взаимодействия соседей, deadline и порядка фаз.
На срезе 589 полный `movement` выбирал **48 SIM + 6 nav**, включая удаление грунта под стоящей
стопой, реклейм, неровную поверхность, thin rails и `safe_lanes…`. Эти интеграционные
проверки не все отбираются quick: их нельзя считать доказанными без явных фильтров.
`--list` показывает только inventory, а не прохождение тестов.

На срезе 589 полный movement Codex прошёл; независимо повторены `safe_lanes…` и
`spider_crosses_thin_rails…`, обе прошли. При этом на манёврах сохраняется
planted-скольжение, поэтому replay доказывает повторяемость, а не всю корректность
контакта. Разбор ограничений — [590](analysis/590-step-deadlines-and-contact-review-20261113.md),
предыстория — раздел 9 [analysis/587](analysis/587-locomotion-validation-review-20261113.md).

`--reuse-passed` сначала обращается к Cargo. Затем может переиспользовать
подтверждённое исполнение тех же тестов: SHA executable, настройки сборки,
версия запускателя и журнал реального успешного запуска должны совпасть.
Выбранные тесты должны входить в подтверждённый набор. Это разрешено только
для проверенных модулей механики SIM и libtest nav/fx. Документация, сценарии,
тесты внешних файлов и создания preview исполняются заново. В отчёте отдельно
записаны `reused_passed` и копия доказательства; они не выдаются за новые тесты.
Без флага все тесты выполняются. Для нового замера времени флаг не используется.
Это ручной whitelist, а не доказательство чистоты будущих тестов: новые runtime
assets, environment inputs и временные assertions требуют пересмотра разрешения.

Fingerprint учитывает также файлы из прямых строковых `include_str!` и
`include_bytes!`, в том числе канон экономики и WGSL. Сложные макросы и внешнюю
среду подтверждает обычная сборка Cargo; `--no-build` остаётся ручным строгим
режимом и не совмещается с переиспользованием результатов.
В `movement` включены проверки упрощённой опорной сетки для шагающих и
сравнение последовательной/отложенной фазы ног. Последнее проверяет также
Commander и Walker04: поздняя постановка ног не должна менять уже принятую
позицию корпуса, которую читают соседние юниты.
Полный набор также включает `body_inertia_tests` и `leg_clearance_tests`;
короткий набор не подтверждает эти более дорогие контракты.
На Windows Python выбирает доступный `pwsh`, а при его отсутствии `powershell`.
Дочернему процессу передаются `-NoProfile` и `-ExecutionPolicy Bypass`, как в штатных
командах репозитория; системная политика не меняется.
Профиль `sim-test` включает базовую оптимизацию, incremental и 256 codegen units,
полностью отключает LTO. Проверки переполнения и debug assertions сохранены.
Игровой `release` и его настройки не изменены. Это отдельная папка
`target/sim-test`, не замена игры по ярлыку.

Первая сборка остаётся затратной. Ускоряется выполнение реальной SIM и последующий
цикл; компиляция, перечисление и выполнение измеряются отдельно. После изменения
профиля Cargo пересобирает зависимости один раз. Результаты этого профиля не
используются как замена release-бенчмарку или замеру FPS.

Запускатель один раз собирает каждый выбранный test target, извлекает настоящий
путь executable из Cargo JSON, читает inventory и запускает объединённый список
точных имён. Неверный фильтр, ноль реально выполненных тестов, только ignored,
несовпадение числа тестов, падение и timeout — ошибки. Повторяющиеся фильтры не
запускают один тест дважды. Изменение исходников во время сборки запрещает stamp.
Проверяются также точные имена и статусы каждого исполненного теста, а не только
цифры итоговой строки. Замена executable или запускателя во время проверки
отклоняет результат; изменённый executable не получает запись pass в кэше.

В `out/fast-tests/latest/test-index.json` находятся имена, числа passed/failed/ignored,
время сборки/тестов, SHA executable, fingerprint Rust/RON/Cargo и настройки сборки.
Логи лежат рядом. Для сравнения прогонов задавать разные `--out`.

`--no-build` применять только после завершения сборки. Если другая команда меняет binary
или исходники, stamp отклоняется: это не разрешение использовать старую версию. Fingerprint
покрывает Rust/RON/Cargo-файлы и настройки, но не доказывает всю внешнюю среду или assets.

На Windows процесс скрыт, приоритет BelowNormal, маска CPU 5; сборка — максимум
два задания, libtest/Rayon — один поток. Проверки последовательные. Тайм-ауты:
сборка 600 с, один тестовый процесс 180 с; можно явно изменить. При timeout
останавливается только дочернее дерево этого запуска.
`test-fast` и `motion-lab` используют общую системную блокировку на рабочую папку.
Второй запуск сразу сообщает о занятом проверяющем процессе; он не начинает
параллельную тяжёлую работу и не ждёт скрыто в очереди. ОС освобождает блокировку
при завершении владельца. Отдельные внешние команды Cargo и запущенная вручную
игра этой блокировкой не управляются.

Наборы — целевые проверки, не замена полного workspace перед приёмкой большого
пакета. Для конкретной правки сначала профильная регрессия; общий набор расширять
при новом отказе или затронутом контракте. Полный бой/4К нужен для проверки
масштаба и итогового представления, а не после каждой правки формулы.

## Графическая зависимость demo

Обычные тесты demo и матчей не подключают render/Bevy/wgpu. Раньше графика
подтягивалась ради одного benchmark, хотя библиотека сцен её не использует.
Для него требуется явный opt-in:

```powershell
pwsh -File scripts/cargo-local.ps1 run --release -p demo --features render-tools --bin bench_cull_world
```

Полный workspace по-прежнему включает render как самостоятельный пакет.
Это отделение зависимости, а не отключение рендера у самой игры.

## Походка: один прогон, много просмотров

```powershell
python scripts/motion-lab.py --scenario flat --out out/motion-lab/flat
python scripts/motion-lab.py --scenario terrain --out out/motion-lab/terrain
python scripts/motion-lab.py --scenario terrain --kind commander --out out/motion-lab/commander
python scripts/motion-lab.py --scenario tracks --out out/motion-lab/tracks

# Пересчитать отчёт или сравнить CSV без повторного запуска SIM.
python scripts/gait_report.py --input out/motion-lab/flat/gait.csv --out out/gait-view
python scripts/gait_report.py --input out/after.csv --baseline out/before.csv --out out/gait-diff
```

`motion-lab.py` собирает существующий `bench_gait` тем же быстрым профилем.
Все три опыта используют реальный BlastRange: 300 тиков на модель, snapshot
после тика 45 и сравнение каждого последующего hash при 1/2 workers. Есть восемь
снимков стадий на модель. `tracks` проверяет шесть гусеничных классов; остальные —
четыре шагающих. Внутренние assert runner остаются обязательными.
`--kind` ограничивает опыт одной моделью, сохраняя 300 тиков и все сверки.
Каждый запуск пишет исходные CSV/snapshots в отдельную `runs/<id>`; manifest
указывает этот каталог. Старые файлы не засчитываются как результат нового
запуска. HTML/SVG и итоговый manifest остаются в выбранной папке `--out`.

Результаты:

- `manifest.json`: SHA binary/CSV/snapshots, fingerprint compile inputs, сценарий,
  workers, отдельные времена сборки и симуляции; ошибка не становится success.
- `run_directory`: уникальный `runs/<uuid>` для staged snapshots и CSV нового прогона.
  Неполный набор снимков не спасает файлы прежнего запуска. `--kind commander` запускает
  только эту модель; неизвестное имя отклоняется до симуляции. Проверки
  `test_motion_lab.py` охватывают полный набор, неполные снимки, изоляцию вывода
  во временном каталоге, дубли summary, сбой анализа и замену executable.
  `manifest.success` устанавливается только после завершения анализа и проверки
  неизменности executable/запускателя; финальный статус передаётся и в `metrics.json`.
- `index.html`: просмотр уже записанной походки с ползунком и проигрыванием,
  сверху/сбоку, один масштаб для всех тиков модели. Открывается обычным браузером.
- `poses.svg`: лист ключевых поз без запуска браузера или игры.
- `metrics.json`: минимальное planted, нулевые planted-тики, отрывы, остаток IK,
  максимальное и суммарное смещение последовательных planted-контактов.

Можно передать `--binary путь/bench_gait.exe` для **явно выбранной замороженной**
версии. Такой manifest отмечен archival: текущие исходники не выдаются за
доказанные входы старого executable. Анализ CSV без manifest также помечается
как архивный. Это защищает от сравнения случайных версий из target.

## Границы диагностики

Зелёный planted — сохранённое состояние контакта, не доказательство несущей силы.
Линия root→ankle — схема, не геометрия кости. CSV округлён до миллиметров;
`lift_mm` измерен от исходного уровня пола, не от текущего рельефа. Здесь ещё нет
полных суставов, источника/ревизии опоры, penetration всей подошвы и углового
скольжения. Нулевые planted-тики/IK residual показываются явно, но не маскируются
под автоматически пройденную физическую приёмку. Для tracks CSV содержит строку
корня без ног; показатели стоп к нему неприменимы.

CSV также не разделяет сохранённый anchor и фактический contact, не записывает
`Contact.head/normal`, `swing/progress/cadence`, `allow_liftoff`, срок посадки другой
ноги и причину reset/lane-fit/recovery/side-clamp. Поэтому анализ смещений надо дополнять
ограниченной event trace, а не только новым глобальным порогом по planted.

Временный низкоуровневый probe воспроизвёл на настоящей `Foot` **41,289 мм** горизонтального
сдвига при первом повороте около 3,5° на плоском полу, сохранив `planted=true`.
Он остановлен намеренным assert и затем удалён; это диагностика существующего дефекта,
а не новая регрессия или принятое исправление. Доказательство — `out/review592-lane-probe`,
разбор и необходимый следующий trace — [593](analysis/593-planted-anchor-and-motion-window-review-20261113.md).

Для живого мира дополнительно нужны сценарии resting → moving под уже поставленной
подошвой, смена источника на одинаковой высоте, частичная опора на малый фрагмент и
движущийся обломок через swing. Trace должен различать источник/ревизию и относительное
смещение по носителю. Replay не доказывает правильность такого контакта. Варианты и
критерии приёмки — [594](analysis/594-moving-support-and-debris-contact-review-20261113.md).

Следующий уровень событийной диагностики должен разделять `contact_tick` и `ready_tick`,
источник/revision и причину Pending/Rejected. Нужны отдельные проверки частичной подошвы,
moving-носителя и переноса веса у двуногого; успешный planted/replay не доказывает `Ready`.
Это предложенные проверки, а не уже существующие тесты. Методика — [595](analysis/595-support-readiness-and-acceptance-review-20261113.md).

Для изменения анимации следующий уровень — proxy 3D по настоящим seg_frames,
затем редкая native-проверка 4К. Blender должен получать готовую SIM-позу,
не рассчитывать вторую походку. Rerun/новый движок сейчас не требуются.

Для локализации дорогой фазы у уже собранного `bench_gait` есть узкий режим:

```powershell
target/sim-test/bench_gait.exe --terrain --kind commander --profile --out out/commander-profile
```

Родительская папка `--out` должна существовать. `--kind` выбирает одну модель;
неизвестное имя завершает запуск ошибкой. Без него выполняются все четыре.
`--profile` читает существующие наблюдатели фаз, печатает восемь самых дорогих
категорий и сохраняет обычные проверки snapshot/hash. Часы находятся только в
диагностическом executable; его время с включёнными наблюдателями нельзя
выдавать за FPS или сравнивать напрямую с запуском без наблюдателей.

Настройки профиля сверены с [Cargo Book](https://doc.rust-lang.org/cargo/reference/profiles.html).
Отключён именно LTO через `"off"`: `false` в Cargo ещё допускает thin local LTO.

Дополнительная диагностика восьми ног и тонких препятствий:

```powershell
pwsh -File scripts/cargo-local.ps1 run --profile sim-test --offline -p sim-core --bin bench_spider_steps
```

`bench_spider_steps` прогоняет высоты 0/8/14/20/28/44 вокселя для прямого
приказа и pilot. Печатает прибытие, blocked, минимум planted, нулевые опоры и
максимальное смещение **фактически решённого IK ankle** за тик. Assertions и
manifest нет, поэтому код выхода 0 не означает приёмку: оценивать нужно числа,
трассу и визуальную позу. Это не часть `test-fast --suite movement`.

## Порядок рабочего цикла

1. После локальной правки — точная регрессия и короткий набор затронутой системы.
2. После изменения общего контракта — расширенный набор, включая workers/restore
   и последовательную/отложенную обработку, если затронут порядок фаз.
3. Для походки сначала один проблемный юнит без графики, затем полный набор при
   общей правке. Из готовой трассы можно многократно строить отчёт без новой SIM.
4. Игровой release собирается после завершения исходников и нужных проверок.
   Нативные кадры нужны для визуальной правки; отдельный бой в 4К — для FPS.

Сборка release, повторное исполнение тестов и повторный просмотр одной трассы —
разные расходы. Время каждого этапа записывается отдельно. Проверки работают
скрыто с ограниченными CPU и приоритетом; они не открывают игру и не забирают фокус.

Все проверки Python-инструментов (анализ профилей CPU/GPU, трассы, походка и
запускатели) запускаются одной командой без игры:

```powershell
python -m unittest discover -s scripts -p 'test_*.py'
```

На актуальном срезе независимого ревью выполнены **190/190 OK**; прежние 185 относятся
к набору до добавления UTF-8 guard. Печатаемые fixture ошибки анализа, замены binary
и неполных snapshots — ожидаемые отрицательные случаи. Методика и отличие новых тестов
от reuse — в отчётах [586](analysis/586-validation-cycle-review-20261113.md) и
[587](analysis/587-locomotion-validation-review-20261113.md).

При красном тесте хвост вывода записывается в консоль байтами UTF-8. Русский panic в
Windows больше не заменяется вторичной ошибкой cp1252; исходный log не меняется,
`success=false` и failed count сохраняются. Отдельный regression закрывает этот случай.


## Паук и тонкие барьеры

Быстрая регрессия реального привода:

```powershell
python scripts/test-fast.py --package sim-core --filter spider_crosses_thin_rails_both_ways_without_stalling_or_losing_all_supports --out out/spider-rail
```

Тест охватывает обе стороны барьеров 0 / 0,8 / 2 / 2,8 м, задержку первого
движения, прибытие, лишние блокировки и полный отрыв опор. Он включён в
`--suite movement`; отдельный запуск не нужен после успешного полного набора
на той же сборке.

`bench_spider_steps --height 28` — детальная диагностика Motion, не отдельная
физика. `direct=true` означает заранее заданный прямой путь, не управление Pilot.
Метрика `foot_delta_mm` относится к фактически решённому IK ankle;
`stance_delta_mm` — только к двум последовательным planted. Старые логи,
считавшие расстояние сохранённых целей, с ней напрямую не сравниваются.

`bench_gait --barriers --kind spider --out out/spider-barrier` запускает настоящий
BlastRange с тонким барьером 2,8 м, управлением Pilot, 300 тиками и восстановлением
на 45. Каждый следующий hash сверяется между одним и двумя работниками.
Выдаёт CSV и штатные снимки для native render. Переиспользовать headless-снимки
для кадров выгоднее, чем заново воспроизводить весь опыт с графикой. Каталог
`--out` должен существовать. `barrier-manifest` связывает binary/source/log/snapshots;
`barrier-report` строится из готовой трассы без повторной SIM. Replay и остановка
не отменяют planted-slide и swing-ошибки: их разбор и независимый повтор —
[590](analysis/590-step-deadlines-and-contact-review-20261113.md).

## Серии взрывов и повторные кратеры

```powershell
# Только четыре проверки геометрии/replay/drain повторных и пересекающихся волн.
python scripts/test-fast.py --package sim-core --filter multi_crater_tests:: --out out/multi-craters
```

Независимый запуск четырёх multi-тестов дал **4/4 passed** на `ea212bd1…`. На последнем

четыре теста; доказательство — `out/review591-craters-budgets/test-index.json`.
До изменения admission-only оракула прежний расширенный запуск дал 19/1 в
`small_fragment_pool…`. Новый оракул явно освобождает занятую ёмкость и подтверждает
completed, поэтому старый отказ нельзя приписывать новому входу.

Политика admission сравнивается на неподвижном грунте с достаточным конечным бюджетом
и явным освобождением вместимости. Она не моделирует приземление и не подменяет отдельные
живые BlastRange-опыты. Заполненный пул может задержать контакты в режиме ожидания;
сам по себе срок ожидания не доказывает потери работы. В последнем multi-стенде
`max_flying=hull_piece_reserve+16`, а assert требует настоящие ground fragments:
проверка не проходит только через pulverize из-за занятого телами резерва.
Пересекающийся залп дополнительно проверен при `edits_per_tick=65536` и `1024`;
для штатной квоты задан предел 16 тиков именно этой сцены, а не любого боя или
времени реакции юнита. Обе конфигурации входят в один libtest, не удваивая inventory.

Это **не полная приёмка движения через динамический кратер**. Multi-сцена держит корпуса
вдали от эпицентра, а отдельный тест объезда использует заранее созданную яму и не
проверяет посадку стоп или мелкие обломки. Отдельный diagnostic на прежнем входе
`4af86ed6…` не завершил drain за 600 тиков при внутреннем `pending=161`; это основание
для телеметрии deferred hit, а не доказательство бесконечного deadlock в новой сцене.
Долгая волна, допустимый переход и сила опоры — разные контракты.

### CPU-сценарий native-боя

`bench_battle --playable-world --ai-vs-ai --ticks 299 --workers 2 --physics-workers 2 --tick-csv out/playable-cpu.csv`
использует тот же стартовый мир, что native world-battle: слой subsoil редактора,
высоту расстановки, строительный двор, живую экономику и стандартную конфигурацию
оружия. Старый authored-сценарий `--world` остаётся отдельным режимом.

Для CPU-замера используется оптимизированный GPU-free профиль. При сборке через
`sim-test` дорогие debug assertions полного мира отключаются отдельно:
`--config profile.sim-test.debug-assertions=false`; overflow checks сохраняются.
Число Rayon workers задаётся явно вместе с physics/navigation workers. CSV учитывает
появление новых акторов при производстве. Начальные входы и итоговый authoritative
hash сверяются с native-сценарием при одинаковом числе тиков.

Интервалы тиков этого режима не являются FPS. Боевой FPS измеряется отдельно по
фактическим frame-start интервалам native release в активном бою с записанными
разрешением, workers, нагрузкой мира и памятью.
