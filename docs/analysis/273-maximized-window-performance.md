# Развёрнутое окно как основной режим приёмки — 13.10.2026

Пользователь обычно разворачивает окно игры на весь экран. Поэтому
результаты прежних native-прогонов 1600×900 относятся к контрольному
оконному режиму, а не к его обычному режиму игры. Основная дальнейшая
приёмка производительности проводится в развёрнутом окне на текущем
мониторе. Exclusive fullscreen и изменение системного разрешения не нужны.

## Воспроизводимый запуск

`blast --maximized` отправляет запрос разворачивания через Bevy Window.
`scripts/profile-range.ps1 -Maximized` передаёт этот флаг, записывает
RequestedMaximized в manifest и требует подтверждения от исполняемого
файла. Старые замороженные бинарники, молча пропускающие неизвестные
аргументы, не проходят такую проверку. Обычный запуск без флага и прежние
явные размеры `-WindowWidth`/`-WindowHeight` сохраняются для сравнения с
историческими результатами. При разворачивании эти размеры задают только
восстановленное окно; измеряется фактическая клиентская область.

Двухсекундный прогрев начинается после готовности ресурсов. Контекст
измерения фиксирует physical_size, scale_factor, focus, present_mode,
window_mode и камеру. Изменение контекста в измеряемом интервале делает
сравнение невалидным. `Windowed` в этом контексте совместим с развёрнутым
окном Windows; это не свидетельство окна 1600×900. Подтверждение CLI
свидетельствует о запросе, не заменяет проверку реального размера.

Основной стенд: world-battle/AI-vs-AI, штатные данные и эффекты, 120 секунд,
physics4/navigation8/Rayon4/Compute4, TargetFps165, без записи кадров.
Графические и CPU диагностические запуски не смешиваются с обычными.
Сборки, тесты и форматирование выполняются вне native-измерений.

## Замер

Монитор по Windows: 3840×2160, 164 Гц; основная клиентская область после
разворачивания 3840×1949 (7 484 160 пикселей, в 5,197 раза больше
1600×900). Read-only проверка Win32 IsZoomed подтверждает разворачивание,
GetClientRect при DPI-aware потоке — реальные размеры, GetDpiForWindow —
288 DPI / системные 300%. В Bevy остаётся прежний scale_factor override
1.0: это эффективный масштаб приложения, не измерение системного DPI.
Проверка ОС не переключает фокус, не меняет окно и не снимает кадры;
исключается служебное окно процесса с нулевой клиентской областью.

Одна хронологическая пара A→B, по 120 секунд. Обе записи имеют
ValidForComparison=true, AcceptanceEligible=true и проходят rate gate.
Фокус, клиентские пиксели, эффективный масштаб, камера, входные данные
и адаптер совпадают; render_context_changed=false. ОС независимо
подтверждает одинаковое развёрнутое окно. Build/test/capture конкурентов
семплер не обнаружил. Запуски используют AutoNoVsync, как прежний
профилировочный стенд; обычный realtime-сеанс игры может использовать
AutoVsync, поэтому это не отдельное измерение задержки вывода с VSync.

Разница −1,0% FPS не доказывает устойчивую регрессию или ускорение:
это одна пара, а горизонт ограничен стенными 120 секундами и заканчивается
на разных соседних тиках. Хеши на разных тиках напрямую не сравниваются.
Для каждого запуска отдельно продолжен снимок3200 тем же вариантом ядра
до его конечного тика: A3600 `c7f2c4f503986ec3`, B3601
`b83c133ff503f3c8`; оба точно совпали с native. Дополнительная
верификация невременных траекторий ADR-701 остаётся в 272.

Прежняя пара 1600×900 в 272 дала 78,785→78,219 FPS. Оба новых значения
примерно на 31% ниже своих прежних оконных результатов. Это важный
практический ориентир, но не чистая оценка цены одного пикселя: между
сессиями меняются время запуска и форма viewport, последняя влияет на
видимый охват при тех же camera_controls. GPU timestamps в этих двух
прогонах не включались; утверждение «всё упирается в GPU» не установлено.
Цель каждого кадра ≤6,06 мс /165 FPS не достигнута.

Проверки изменения стенда: 128 Python-тестов анализатора, PowerShell
набор валидности с шестью случаями нового режима, 135 render library
тестов (2 ignored), 12 проверок архитектуры и 3 связности документов,
форматирование, сборка обоих release-бинарников.
Проверка ОС первоначально обнаружила также нулевое служебное окно;
read-only наблюдатель уточнён и повторён. Это не изменение окна игры
и не сбой native-прогона. Повторных полных тестов симуляции для CLI-флага
не требовалось; их результаты относятся к ADR-701 в 272.
Raw: `out/maximized-20261013/`. Обе версии получают одинаковое изменение
запуска окна. A использует исходный burst.rs до ADR-701 (e3ad587), B —
локальную связность ADR-701 (c6221a9). Сохранены build-логи, SHA256
бинарников и перечисленных исходников. Основной burst.rs восстанавливается
побайтово; release-полигон в target после сборок соответствует B.
