# Сохранение навигационного кэша равных завалов — 16.10.2026

Первый точный срез [плана316](316-optimization-delivery-plan.md), OPT316-01.
База — main `46f5987`. Причина найдена в
[архитектурном аудите315](315-performance-architecture.md), измерительная
база большого боя — [314](314-global-performance-audit.md). ADR-743.

## Изменение

`BlastRange::refresh_rubble` уже сравнивал новую карту завалов с прежней,
чтобы не обновлять равные отпечатки страниц. Но после сравнения безусловно
присваивал новый Rubble, в котором `OnceLock` для coarse debris tiles пуст.
Общие плитки использовались несколькими маршрутами одного тика, после
равной пересборки следующего тика строились снова по запросу.

Теперь `self.rubble = rubble` находится внутри прежней ветки изменившегося
или первого входа. Точное равенство отсортированных колонок сохраняет
прежний объект, spatial index и ленивые coarse tiles. Первый refresh
после construction/restore и изменённая карта проходят прежний путь.
Частота SIM, порядок движения, квоты, урон, физика, snapshot/hash и
observer schema не меняются. Новых gameplay-констант и зависимостей нет.

Это исправление общего движка; режимы, сценарии и стороны не различаются.
Полное построение новой входной карты и опор **по-прежнему выполняется**.
Это не persistent support index из OPT316-04 и не решение всех лагов.

Кэш coarse tiles — чистая функция колонок и размера мира. Material/floor
tiles земли инвалидируются отдельно сразу при правке мира. Поэтому
сохранение равной rubble-карты не задерживает видимость новых ям.
Для непустой километровой карты dense таблица содержит1 562 500 значений
u16:3 125 000 байт, около2,98 MiB. Пустые/большие карты имеют свои прежние
пути. Сохранение объекта не означает, что каждый тик обязательно просил
coarse tiles или сэкономил ровно это число байтов.

## Частота возможности переиспользования

В прежнем `bench/world-a.csv` аудита314:2568/6000 шагов имеют нулевые
changed_columns и full_builds, в последних600 —435. Это косвенный признак
равной карты по прежним счётчикам print, не число фактических coarse builds.

В новой диагностике позднего snapshot отдельно сравнивается адрес первой
колонки между шагами: при построении новый массив существует одновременно
с прежним, поэтому замена непустой карты не может сохранить этот адрес.
Это проверяет удержание объекта без изменения SIM и без полного сканирования
истории. Количество unchanged определяется прежними print-счётчиками.
Прогрев пустой карты в этот адресный счётчик не входит.

Для оценки используются весь tick и целые фазы motion/rubble. В равной
ветке новая временная карта освобождается при выходе из функции, после
метки `rubble_print_end`, но до завершения полной фазы rubble. Снижение
только `rubble_print_us` поэтому нельзя целиком считать выигрышем:
часть освобождения буферов перешла за эту вложенную границу.

## Воспроизведение и происхождение

Артефакты — `out/optimization-317`. Проверены все497 исходных файлов и
файлов данных из installed-аудита314: до изменения они точно совпали.
Frozen `before-bench_battle.exe` совпал с installed binary SHA256
`40a1a848f2c066a3ae52f8f6f20f96fff150134e8f438eeea2242629f5c6d964`.
Before production rlib также сохранён; hot driver компилировался с ним
до production-сборки кандидата. Новая версия driver одна для обеих сторон.
Это проверка content provenance, не аттестация чистого toolchain build.

Hot workload: snapshot `out/performance-audit-20261016/headless/18.bin`,
tick6000/hash `21bef878463f364c`, physics4/nav8/Rayon4,30 шагов прогрева,
300 измеряемых шагов, одинаковые входы. Часы только в вызывающем driver;
проверка адреса/счётчиков и финальный hash выполняются вне времени шага.
Сборки, тесты и физические измерения не выполняются одновременно.

Источники driver/build/analyzer, CSV, логи, fingerprints и бинарники
сохранены рядом. `hot.rs` включает полные фазовые времена и вывод
`RUBBLE map_retained/unchanged/measured`; `analyze.py` агрегирует ABBA.
`artifact-manifest.json` содержит SHA256/размеры артефактов, отчёта и
использованного внешнего snapshot. Source fingerprints подтверждают,
что runtime inputs не менялись между сборкой и завершением проверок.

Для проверки конкретного потребителя выполнена отдельная ABBA-серия

throughput и фризы остаются открытыми. Следующий приоритет — OPT316-02a.

## Границы результата

Сохранение равного объекта устраняет конкретную потерю cache lifetime.
Оставшиеся задачи — спекулятивное чтение больших взрывов, долг очереди
валки, полная сборка rubble/support, активные ID и отдельный SIM owner.
Радиус и мощность T3 не сокращаются. Меньшее число пересборок само по
себе не доказывает ускорение всего кадра,165 FPS или устойчивость World.
