## Что измерялось, а что было потеряно

| Область | Покрытие до изменения | Изменение / оставшийся предел |
|---|---|---|
| Все штатные фазы BlastRange::step | Завершения фаз, вложенные детали, monotonic clock | Сохранены; необозначенный хвост остаётся явным |
| Physics/navigation workers | Идентификаторы потоков, интервалы задач, полные суммы и самые длинные выборки | Сохранены; wall параллельных задач не складывается со сроком фазы |
| AI и оружие | Отдельные этапы приказов, LOS, навигации, полёта, capture/frontier/wave, лазера, тепла | Среднее по неактивному пути не доказывает дешевизну оружия во всех сценах |
| Отображение юнитов и обломков | Отдельные unit_mesh/fragments интервалы | Сохранены; детализация по каждому типу меша пока агрегирована |
| Terrain/occupancy/газ на CPU | Вложенные интервалы Update, реальные extract/prepare calls, transfer counters | Сохранены; последние атомарные render_prepare_ms в CSV не считаются новой работой каждого кадра |
| Bevy вне игровой цепочки Update | Попадало в общий промежуток между кадрами | Добавлены main_after_update и main_before_update_next |
| Подготовка и отправка рендера | Timeline и дополнительный render-tasks build | Отдельный прогон с фактическими system spans; сборка с этим feature не используется для FPS-приёмки |
| GPU | Только агрегаты строк GPU в stdout; анализатор их игнорировал | Исходный gpu.csv, статистика проходов и совместно опубликованных наборов |
| Свои постпроцессы | Не было отдельных меток edge/occlusion | Добавлены voxel-edge и voxel-occlusion |
| Отсутствие/обрезание GPU-данных | GPU-флаг мог пройти без данных; GPU-only мог считаться обычным FPS | Пустые/невалидные/обрезанные записи запрещают сравнение, GPU-only всегда diagnostic |
| Потеря или задержка GPU-публикаций | Число выборок не объяснялось | Явное число наборов/кадров; CPU frame ID не приписывается задержанной выборке |
| Холодный запуск, сохранение/загрузка, строительство/экономика | Отдельные headless benches; часть сценариев не активирует эти пути | Не входят в таблицу среднего боя; для них нужны собственные workloads |
| Present/драйвер/причина сна потока | Только общий submit_present_tail и грубые OS-счётчики | Точная атрибуция блокировки требует отдельной системной трассы; ожидание не объявляется GPU-временем |
| Давление ОС и память процесса | CpuThreads/OsPressure сохраняют PrivateBytes, WorkingSet, faults, системный commit и интервальные CPU counters | Это периодические samples, без стека аллокаций, точного кратковременного пика и стоимости/объёма каждого GPU-ресурса |

Нельзя утверждать «профилируется абсолютно всё». Сетевое ожидание,
дисковые задержки, стеки аллокаций/короткие пики памяти и каждая функция Bevy не
атрибутируются этим стендом. Для горячего пути игры теперь есть явные
границы крупных фаз и необъяснённый остаток; это позволяет выбирать
следующую детализацию по измеренной цене, а не по подозрению.

## Контракт новых данных

Timeline schema5 добавляет две границы MainScheduleOrder без изменения
порядка отдельных параллельных систем. main_after_update включает
SpawnScene/PostUpdate/Last; main_before_update_next включает
First/PreUpdate/RunFixedMainLoop следующего кадра и относится к предыдущей
строке Update. Они лежат в её следующем промежутке, не внутри тика.
Прогрев без FrameSource не записывается; закрытый capture не растёт.
Лимит планируется на 15 scopes×400 кадров/с, максимум 1 000 000 записей.

GPU schema1 сохраняет observation_row, available_ns, path, elapsed_gpu_ms.
available_ns — момент публикации Bevy на CPU относительно эпохи профиля,
не начало исполнения на GPU. Измерение прогрева, повтор одной публикации
и устаревшее значение исключаются. Глобальный лимит 1 000 000 выборок;
переполнение, некорректные значения и отсутствие данных отражаются явно.
Внутри измерения нет записи файлов; CSV и сводка сохраняются после него.

Bevy передаёт последний готовый набор через один слот. Некоторые GPU-кадры
могут не попасть в DiagnosticsStore; исходный кадр не доступен в этом API.
Поэтому сумма наблюдавшихся соседних scopes на публикацию не называется
временем всего GPU-кадра, а отсутствующий проход — доказанным нулём.
Родительские scopes не складываются с дочерними. Старые логи доступны как
legacy_aggregates_only; для них нет выдуманной групповой суммы.

без обрезания и невалидных значений. Таблица делит сумму наблюдавшихся

проход не наблюдался. Это общий знаменатель, а не сумма условных средних
каждого региона. Он не восстанавливает потерянные GPU-кадры.

Газ даёт около 71% суммы наблюдавшихся GPU scopes. Дорогой путь —
**рисование объёмных облаков по пикселям**, а не вычисление самого поля
газа. В текущей сцене восемь региональных проходов; каждый использует
полноэкранный треугольник и собственную трассировку. Цена зависит от
покрытия экрана, глубины и количества пересекающихся регионов. На большом
viewport это первый кандидат для следующего измеряемого улучшения.
Метка охватывает весь gas composite: кроме трассировки объёма, там есть
освещение, тени и смешивание VFX. Разделение миллисекунд между функциями
внутри одного шейдера этим timestamp не установлено.
EdgePlugin в blast не подключён, поэтому отдельного voxel-edge в этой
записи нет; отсутствие метки не объявляется нулевой ценой активного прохода.

### Подготовка рендера: wall не равен занятости CPU

RenderTasks записал 264 252 завершённых интервала без потерь, с шагом
семплирования 8: 722 исходных кадра. Render prepare в целом занимает
9,738 мс wall в среднем, но внутри него есть ожидание.

| Система RenderApp, выборка с шагом 8 | Среднее wall, мс | p99 wall, мс | Среднее calling-thread CPU, мс |
|---|---:|---:|---:|
| prepare_windows | **5,139** | **24,598** | **0,043** |
| allocate_and_free_meshes | 0,938 | 4,887 | 0,844 |
| collect_meshes_for_gpu_building | 0,665 | 1,487 | 0,519 |
| render::gas::prepare | 0,460 | 1,348 | 0,346 |
| collect_visible_cpu_culled_entities | 0,350 | 0,908 | 0,411 |

CPU-счётчик Windows имеет грубую дискретность; последняя строка показывает
предел точности коротких интервалов. Складывать wall параллельных систем
нельзя. В pinned Bevy 0.19.1 `view/window/mod.rs::prepare_windows` получает
surface texture через get_current_texture; комментарий самого движка
указывает на возможную блокировку при GPU bottleneck. Большой wall при
малом CPU и дорогие GPU-облака — сильное указание на обратное давление
графического конвейера. Точная причина конкретного ожидания требует ETW/
PIX/драйверной трассы и этим аудитом не доказана. Оптимизация арифметики
prepare_windows сама по себе не обещает вернуть эти пять миллисекунд.
Совмещённые с capture интервалы OS-семплера дали 294 843,75 мс CPU
процесса за 118 330 мс wall — около 2,49 эквивалента занятого ядра.
Это не «процессор свободен на критическом пути»: серийный участок,
ожидание GPU и незанятые worker-потоки могут существовать одновременно.
Число потоков само по себе не доказывает доступный выигрыш от распараллеливания.

## Приоритет следующей работы

1. **GPU газ в развёрнутом окне.** Проверять общий renderer: экранные
   границы регионов, отсечение скрытых/пустых участков, сокращение повторной
   трассировки пересекающихся облаков. Сначала сохранить разрешение и
   качество изображения; варианты half-resolution/temporal reconstruction
   оценивать отдельно, с визуальной приёмкой. Не уменьшать физические
   объёмы, количество взрывов или авторитетное содержимое газа ради FPS.
   Ограничение scissor само по себе недостаточно: текущий post_process_write
   меняет местами текстуры, поэтому нужно сохранять изображение вне региона,
   а также протяжённые тени/свет и корректный порядок смешивания облаков.
2. **Средняя цена CPU-тика.** Motion commit/routes, перевод и пространственный
   поиск обломков, подготовка опор/завалов. Сравнивать одинаковые workload,
   проверять state_hash/материю и сроки работы. Квоты не подменяют ускорение.
3. **Редкие пики.** Capture/frontier/wave взрывов и строки/occupancy при
   перемещении окна карты. Отбирать конкретные дорогие тики/кадры, чтобы
   среднее не скрывало паузу. Оптимизация грунта остаётся нужна, но не
   объясняет всю цену развёрнутого рендера.
4. **Render CPU и меши.** Аллокатор Mesh, обновление обломков, сбор мешей и
   main PostUpdate. Приоритет ниже текущего gas GPU и ядра; следующий
   уровень детализации выбирается по оставшимся крупным агрегатам.
5. **Отдельные ещё не квалифицированные workloads.** 5000 юнитов,
   массовая копка/экономика, save/load, холодный запуск и memory/VRAM
   pressure. Нынешний бой и camera tour не доказывают их бюджет.

Raw: `out/audit-20261013/`; manifest, log, CSV и analysis сохраняются в
отдельных каталогах. Физика, баланс, квоты, сценарии и save-format

игры из добавления профилировщика не заявляется.

## Воспроизведение

Сначала собрать diagnostic binary, сохранить отдельную копию и её SHA256.
После окончания сборки запустить (PowerShell, из корня репозитория):

```powershell
scripts/profile-range.ps1 -Seconds 120 -Scenarios world-battle -SkipBuild `
  -BinaryPath out/audit-20261013/diagnostic-blast.exe -Output out/new-audit-full `
  -Maximized -PhysicsWorkers 4 -NavigationWorkers 8 -RayonWorkers 4 `
  -ComputeWorkers 4 -TargetFps 165 -CorePhases -RenderTimeline -RenderTasks `
  -Gpu -CpuThreads -OsPressure
python scripts/analyze-range-profile.py out/new-audit-full --require-valid
```

Для камеры: 90 секунд, `-CameraTour`, без RenderTasks/CpuThreads/OsPressure.
Картечь: 120 секунд, `-Scenarios canister`; движение: 30 секунд,
`-Scenarios drive`; остальные диагностические параметры те же, что у камеры,
но CameraTour выключен. У анализатора также указать `--scenario canister`
или `--scenario drive`. Каждый запуск получает новый каталог; анализ и
сборка не выполняются одновременно с native-измерением.

Для обычной проверки пересобрать **без feature render-tasks** и запустить
world-battle120 с теми же viewport/workers, выключив CorePhases,
RenderTimeline, RenderTasks, Gpu и OsPressure. Валидность/темп/контекст
проверять по manifest и analysis, не по одному FPS в консоли.
Raw GPU-CSV и render/task-CSV не заменяют друг друга. Их отсутствие,
потерянные записи или разные контексты не разрешают сравнивать стоимость.
