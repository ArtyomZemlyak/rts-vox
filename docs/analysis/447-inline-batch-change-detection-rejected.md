# 447 — Changed-флаг в stamp-обходе batches: отклонено

2 ноября 2026. Артефакты: `out/optimization-447/`.

## Гипотеза

`Batches::update` сравнивает каждый `Stamp` в основном обходе, а затем снова
выполняет глубокое `self.input != self.scratch`. Прототип вычислял changed-флаг
в первом обходе и устранял повторное сравнение всей истории.

Логика сохраняла различия длины, порядок stamps, группы и публикацию. Lifecycle
wakeup/edits/reclaim прошёл.

## Измерения

Baseline `out/optimization-444/current-825-blast.exe`, после
`after-batches.exe`, SHA-256
`6389f6a473d489dc19b9e795ce6be6aff81535ce974a4a103d04719bfa17bf72`.
Две60-секундные native4K-пары в прямом и обратном порядке. Оба варианта
`ValidForComparison=true`; реального темпа20Гц нет.

| Показатель двух пар | Baseline | После | Изменение |
|---|---:|---:|---:|
|Средний FPS|29,357|28,808|−1,87%|
|`fragments`|6,759 мс|7,154 мс|+5,85%|
|p99 кадра|103,490 мс|105,096 мс|+1,55%|
|1% low|8,950 FPS|8,797 FPS|−1,71%|
|`simulation_core`|15,579 мс|15,812 мс|+1,49%|

Обе серии дали замедление. Встроенное глубокое сравнение Vec оказалось эффективнее
дополнительной changed-логики в горячем stamp-обходе. Это не доказанный owned-delta
выигрыш и не улучшение frame pacing.

## Решение

Прототип отклонён, `batches.rs` полностью возвращён к baseline без diff. ADR не
создаётся. Повторное сравнение само по себе не является достаточным доказательством
горячей стоимости; устранять его нужно только при измеренном положительном полном
кадре.
