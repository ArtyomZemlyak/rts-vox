# Ограниченный захват фаз вокруг медленного тика — ADR-535

Дата: 03.10.2026. Продолжение [128](128-stall-slices-and-realtime-acceptance.md).

## Исправленный пробел

Обычный профиль обнаруживает длинный core-вызов, но не сохраняет его
внутренние фазы. Постоянная полная worker-трасса меняет нагрузку и может
занимать сотни мегабайт. Добавлен отдельный opt-in `phase_ring`:
`--profile-trigger-ms 50` вместе с `--profile`, либо
`-TriggerMilliseconds 50` в `scripts/profile-range.ps1`.
Он несовместим с `--profile-core` / `-CorePhases`.

Сборщик наблюдает фазы и детали авторитетного шага. При core wall ≥ порогу
он сохраняет до 16 предыдущих тиков, текущий и 16 следующих. Медленные
тики внутри следующего окна не продлевают его. Лимит — четыре окна;
дальнейшие пересечения порога считаются отдельно. В конце сохраняются
также последние 16 тихих тиков: отсутствие срабатывания не теряет контроль
работоспособности. Верхняя граница — 148 сохранённых тиков, а не фиксированное
число байтов: количество callback-записей зависит от сцены. Смена поколения
очищает старый контекст и прерывает незавершённое следующее окно.

Внутри шага нет файлового IO, worker-сборщика и его блокировок. Запись
`*.stall.csv` происходит после измерения. На каждой границе фазы остаются
монотонное время и ID вызывающего OS-потока; CPU time/cycles снимаются
только в начале и конце тика. Первоначальный вариант снимал CPU counters
на каждом callback; из-за повторных order-границ это лишняя работа.
Финальная версия явно объявляет `cpu_sampling=tick_boundaries`; CPU фазы
помечается недоступным, а не нулём. Windows CPU time имеет грубое квантование:
например, в коротком smoke tick wall 28,055 мс и CPU delta 31,25 мс;
это не физически точное время работы внутри данного интервала.

По умолчанию сборщик выключен: обычный шаг не записывает новые отметки,
не снимает новые OS-счётчики и не выделяет историю. Физические результаты
не зависят от наблюдений. Полный `--profile-core` остаётся отдельным режимом
с worker coverage и прежними файлами.

## Проверка и интерпретация данных

Анализатор сохраняет `stall_trace` отдельно от полной core coverage:
это выбранные тики с `partial=true`, без worker jobs/stack/wait.
Проверяются metadata/режим, лимит и счётчики, часы begin/end, уникальность
тика, поколение и принадлежность реальному измеренному Update-срезу,
наличие файла и соответствие CPU sampling. Недостающие тики ожидаемы
в этом режиме и не выдаются за полное покрытие.

Manifest содержит `CoreTriggerMilliseconds`, runtime header и итоговые
счётчики. Разные настройки захвата не допускаются в одну строгую пару.
Любой trigger-run исключён из FPS-приёмки независимо от темпа; валидность
диагностических данных и выполнение 1× показываются отдельно.

Это закрывает часть WBPERF-027: теперь можно связать повторившуюся паузу
с внутренними фазами без постоянной полной трассы. Caller CPU не является
CPU всего процесса, wall−CPU не доказывает mutex/GPU wait. Покрытие workers,
OS scheduling/stack/wait и причина редких фризов этим не закрыты.
В текущей сессии Windows kernel tracing недоступен без административного
токена; проверка WPR показала отсутствие активной записи. Обход ограничений
и альтернативный stack/wait-сборщик не реализованы.

## Обычные нативные проверки

Стоковый world-battle AI-vs-AI, 60 секунд, 1600×900, RTX 5090 Vulkan,
physics/navigation 8/8, target 165 FPS. Замеры последовательные, без
одновременных сборок, тестов и изменений исходников. Захват выключен.
Все сборки содержат одинаковые ранее подготовленные изменения вне этого
исправления; это сравнение замороженных рабочих сборок, не чистых коммитов.

Все пять захватов проходят целостность `--require-valid`, но не FPS-приёмку.
90/120-секундные запуски также не выполняют строгий темп 1×; в финальном
120-секундном запуске отношение симуляции к wall — 0,97153. Стоимость
длинного диагностического боя не объявляется улучшенной: версии прошли
разное число шагов, строгой пары нет. Smoke проверяет срабатывание/лимит,
а не воспроизводит реальный фриз. При пороге 50 мс ни один захват не
сработал; 16 строк тиков относятся только к тихому хвосту.

Финальный тихий хвост: самый долгий сохранённый тик 3499 — 18,015 мс,
motion 6,266 мс, rubble 2,058 мс; CPU всего caller tick 15,625 мс.
Это не объясняет более ранние неинструментированные эпизоды.

runner/analysis/build/test/clippy logs в `out/performance/`.

## Проверки и следующий шаг

8 native core-тестов, 46 Python и 17 PowerShell случаев прошли. Проверены
контекст/повторы/лимит/reset/тихий хвост, отсутствие worker marks и фазовых
CPU counters, равенство снимков обычного, полного и phase-only шагов,
ошибки metadata/часов/идентичности/файла. Release build и clippy прошли;
остались прежние предупреждения type_complexity (voxel и HUD).

Следующий шаг WBPERF-027 — получить настоящий эпизод внутри phase-ring,
затем сопоставить подтверждённую фазу с worker/OS-трассой и исправлять её
причину. Синхронный sim/render WBPERF-002 остаётся: обычный core здесь
12,36…12,52 мс против бюджета кадра 6,061 мс. 165 FPS, потеря времени
длинного боя и редкие зависания остаются открытыми.
