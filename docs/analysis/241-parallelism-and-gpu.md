## Видеокарта

Для бюджета ADR-656 видеокарта не годится. Тому три причины.

1. **Бюджет — headless.** Бюджет — это тик стенда без видеокарты.
   Lockstep к тому же идёт со скоростью самого медленного клиента: пир
   без видеокарты всё равно считает свои 41 мс.
2. **ADR-092 ограничивает кандидатов.** Сверяемым ядром может быть
   только интегрирование flow field, пока оно не пройдёт соответствие на
   трёх вендорах. Всё прочее мир должен видеть в том же тике (ADR-089),
   то есть с блокирующим чтением.
3. **Горячий код считает в `Fx`.** Это i64 с `mul`/`div`/`sqrt`, а i64 в
   шейдерах запрещён. Эмуляция или переписывание эталона на i32 меняют
   эталоны.

Разбор кандидатов:

| Работа | Подходит под контракт | Реальная экономия | Вывод |
|---|---|---|---|
| поле волны | да: монотонный max-plus, неподвижная точка | ≤ 0.5 мс: дорогие контакты и материя остаются на процессоре | только как игровое решение (Q-76), оно меняет хеши |
| метки связности обвала | да | около нуля: проверка стоит столько же, сколько счёт | нет |
| столбцы завалов, сортировка осевших по ячейкам | да | < 0.6 мс | нет |
| таблица пола столбцов для поиска | да | 1–3 мс | то же дешевле на процессоре: таблица, обновляемая по списку правок |
| поза корпуса, ноги, обломки, лазер, тепло | нет: Fx, точечные запросы, последовательные бюджеты | — | нет |

Проверка «видеокарта считает, процессор выборочно сверяет» в ADR-092
не описана. Выборка даёт лишь вероятностную гарантию. Пригодна она
только как триггер отключения: при расхождении тик пересчитывается на
процессоре, путь выключается до конца партии. Полная проверка дешева
только для задач с единственной неподвижной точкой, например для волны.

Любой путь через видеокарту требует нового входа данных в `sim-core`.
Это меняет границу слоёв, и решает владелец. Чего нет:
- `wgsl_to_wgpu`;
- проверки размера подгруппы;
- соответствия на трёх вендорах;
- конвейерного чтения.

## Параллелизм с побитовым совпадением

Основание. Мир между стоками очереди правок не меняется: в тике один
сток. Все фазы до него читают один и тот же мир.

Перекрыть фазы целиком нельзя: каждая фаза читает то, что пишет
предыдущая.

```
обвал → крошки → обломки → куски → завалы(T+1) → маршруты
приказы → позы → волны → заявки → тепло → сток → обвал
```

Перекрывать можно внутри фаз.

| # | Изменение | Почему результат прежний | Оценка |
|---|---|---|---|
| A | Движение: подготовка маршрута и грунта одной задачей на корпус (минус барьер). Ноги и поза корпуса i уходят в `rayon::scope` сразу после его фиксации и идут, пока фиксация продолжается | ноги i пишут только корпус i; фиксация j читает `positions`, построенные до ног | −2.5…−3.5 мс |
| C | Волны: параллельная чистая предвыборка (`advance_contacts`, геометрия попаданий); последовательно — только проверки и применение | позы волны заморожены; зависящее от урона остаётся в последовательной части | −1.5 мс |
| D | Обвал: разметка компонент чанков параллельно с собственными черновиками; применение по возрастанию номера чанка | разметка — чистая функция чанка | −1…−1.5 мс |
| B | Фиксация движения: корпуса разбиты на острова по консервативному радиусу взаимодействия, острова параллельно | каждое чтение соседей фильтруется по расстоянию | −1…−2 мс |
| E | Один пул на 4 ядра вместо физического и навигационного по очереди (навигация — 8 потоков при 48+ юнитах); `use_current_thread` | сбор результатов по индексу | −0.5…−1 мс |
| F | Мелочи: очистка черновиков параллельно, повторное использование черновиков завалов, ключи слияния кусков по частям, предпроход приказов по акторам | — | −0.5…−1 мс |

Вместе это −7…−10 мс, то есть 31–34 мс в позднем окне. Безопасные
первые шаги — A и E. Перед B, C и D нужны замеры: стадии фиксации
«hunt»/«plan», подфазы `collapse_*`, счётчики `wave_geometry`,
загрузка навигационных воркеров.

Параллелизм внутри одного поиска маршрута не окупается. Когда ищут 16
корпусов, ядра уже заняты поиском разных корпусов.
