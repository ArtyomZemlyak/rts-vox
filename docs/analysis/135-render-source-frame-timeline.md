# Повторный обзор: привязка CPU-рендера к исходному кадру — ADR-541

03.10.2026, исходный main `e4566bc`. Основной сценарий — 30×30, бой ИИ
против ИИ на всей километровой карте, штатное качество, 1600×900.
Цель остаётся 165 FPS / 6,061 мс при 30 Гц авторитетной симуляции.
Этап исправляет способность локализовать задержку; ускорение не заявляется.
История подтверждённых и отклонённых оптимизаций — [134](134-performance-review-and-frame-triggers.md).

## Что работало и почему одной загрузки CPU недостаточно

Подтверждены сокращение повторных запросов мира/опор и независимые задания
с постоянным пулом и упорядоченным commit (527/528), постоянные render-слоты
и отсутствие пустых Transform writes (531). Не подтверждают общий FPS
малые индексы/маски, увеличение числа заданий и CPU-only микрозамеры;
плохие опыты 529/532/534 откатили. В 536 два сочетания использовали один
контроль: считать их двумя независимыми повторами нельзя.

Последовательный тик всё ещё лежит на критическом пути кадра. Расписание
Bevy переносит его между Compute-потоками: в новой записи роль tick_caller
наблюдается у четырёх разных OS ID. Это одна последовательная цепочка,
а не доказательство четырёх одновременно исполняемых тиков. Примерно
2,4–2,5 эквивалента CPU-ядра на весь процесс не объясняют ни занятость
конкретного этапа, ни ожидание результата, ни работу драйвера.

ADR-540 исправил триггер полного кадра и резерв позднего пика. Но старые
render_prepare/render_extract были последними атомарными наблюдениями;
их повторное чтение нельзя считать новой работой или суммировать по строкам.
GPU timestamps также не имеют исходного frame ID. Поэтому почти одинаковые
долгие интервалы симуляции и рендера было невозможно сопоставить.

## Исправление наблюдаемости

`--profile-render` / `profile-range.ps1 -RenderTimeline` устанавливает
профильный плагин. Обычный режим не устанавливает его ресурсы, callback
wrappers или границы расписания. Дополнительное оборудование записи не
изменяет симуляцию/качество/частоту работы и не проходит FPS-приёмку.

При завершении собственного Update-среза публикуется неизменный tag:
нулевой номер строки main CSV, generation, tick, общий monotonic epoch.
Перед исходным Bevy extraction callback tag копируется в render world;
следующий главный кадр и reset его не меняют. Номер строки различает
кадры без тиков и одинаковые tick в разных поколениях.

Sidecar `.render.csv` хранит следующие CPU wall интервалы:

| Интервал | Что включено |
|---|---|
| pipeline_handoff | Исходный callback RenderExtractApp: получение предыдущего render world через ComputeTaskPool executor, извлечение и отправка. Это не чистое время ожидания. |
| extract_callback | Исходный RenderApp callback целиком, включая entity sync и ExtractSchedule. Это не только копирование GasInput. |
| render_schedule | Render schedule от границы перед ExtractCommands до границы после PostCleanup; First/recovery и работа вне этой области не входят. |
| render_prepare | От той же начальной границы до RenderSystems::Render: применение extract commands, ассеты/меши/виды, очереди и подготовка ресурсов. Внутренние воркеры пока не выделены. |
| render_system | Границы около Bevy render_system: root graph и завершающие submission/readback/present. Между hooks возможны pipeline cache/другие системы Render; это не изолированный function cost. |
| render_graph | Root RenderGraph schedule, в том числе его Submit/Finish. Это CPU wall, не длительность исполнения GPU. |
| submit_present_tail | После root graph до границы после render_system: финальный submit/readback, представление окна, сбор screenshots и overhead границ. Это не изолированный present. |

Границы render schedule/graph — exclusive callbacks на его ведущем потоке;
они не добавляют зависимости между отдельными параллельными prepare jobs.
Это диагностическое изменение расписания с накладными расходами. Каждая
граница хранит Rust ThreadId и, если доступны, OS ID, kernel+user thread CPU
и cycle counters через прежний Windows sampler. Другие платформы сохраняют
null; cycle counts не переводятся в миллисекунды. CPU ведущего потока
не включает воркеров; ноль Windows time delta может быть округлением.

До 100000 интервалов предварительно резервируются в памяти. CSV не пишется
на горячем пути. В конце измерения recorder закрывается под коротким mutex
до выгрузки CSV/логов. Последний открытый span остаётся открытым; renderer
не останавливается принудительно ради полного покрытия. Полные started,
retained/dropped/incomplete, cutoff и pipelined mode пишутся в metadata.
Последняя строка main CSV обычно ещё не передана рендеру: это явный missing
source row, а не придуманный нулевой кадр.

Анализатор проверяет budget/counts, schema/mode, источник и reset identity,
общие clocks/cutoff, driving threads/counters, вложенность и порядок стадий.
Завершённый schedule без обязательных стадий и пропущенное внутреннее
поколение/кадр без объявленных drops не проходят. Открытый терминальный
span или исчерпание лимита остаются явным неполным покрытием. Режим с
трассой нельзя сравнить с обычным как равный контракт или принять по FPS.

Для самых долгих main gaps строятся пересечения с объединением каждого
вида интервалов, а также общий union handoff/extract/render schedule.
Вложенные и одновременные интервалы не складываются. Unobserved/other
означает отсутствие нашего span, а не idle CPU. В отчёте также остаются
исходные ID и counters самых тяжёлых render frames. Наличие пересечения
не устанавливает причину задержки или mutex/GPU wait.

Все четыре `--require-valid` прошли. Сохранена проверка первой строки,
асинхронного перекрытия с последующим main frame и переходов generations.
Ни один прогон не проходит FPS-приёмку. Ordinary также теряет темп:
новая трасса не является единственной причиной проблемы длинного боя.
Диагностический запуск оказался тяжелее; из-за разных шагов/состояний и
одного запуска на режим эта пара не измеряет изолированный overhead.
Такое оборудование записи нельзя выдавать за бесплатное ускорение.

В smoke: gap 14,406 мс, render schedule intersection 14,107 мс,
prepare intersection 9,263 мс. Благодаря общим часам это реальный
участок рендера внутри паузы, а не повторение stale atomic values.

В длинном бою source row 6394 / tick 3013: render schedule 86,909 мс,
prepare 82,783 мс, render_system 4,007 мс, root graph 3,280 мс,
submit/present tail 0,497 мс. Ведущий prepare-поток имеет CPU delta=0
по coarse Windows time и 4033830 циклов; это не нулевая работа и не
доказательство GPU wait. Пересечение с соседней симуляцией нужно
рассматривать вместе, а не добавлять prepare к её длительности.

Худший main interval row 6396 / tick 3015 — 113,194 мс:
предыдущий собственный slice 82,848 мс, core 71,557 мс и следующий
gap 30,346 мс. В gap handoff intersection 24,587 мс, extract 24,555 мс,
render schedule 4,517 мс; общий непокрытый остаток 1,243 мс. Сумма
handoff+extract была бы двойным счётом. Late peak ADR-540 действительно
сохранил interval 113,194 мс, источник generation 0 / tick 3014.

За 120 секунд prepare mean/p99/max 4,654/27,669/82,783 мс;
root graph 2,092/3,401/5,037 мс; tail 0,194/0,488/1,759 мс.
Следовательно, долгий **CPU участок находится до root graph** и/или в
extraction; это локализация измерения, а не заключение о виновном алгоритме.
Общие OS интервалы: 2,384 CPU-core equivalents в diagnostic и 2,531 в
ordinary. OS роли не присваивают всю работу потока одному subsystem:
Bevy executor может исполнять другие задания вне помеченного участка.
Большой фриз одного core tick 500…750 мс здесь снова не воспроизведён.

## Следующие работы по влиянию на понимание

1. P0 — source-frame scopes внутри дорогих extract/prepare: вход/выход
   GasInput extraction, mesh/asset/queue/resource jobs, размеры upload,
   worker busy и critical job. Отделять serial preparation/commit от
   исполнения воркеров, не складывать parent/child и concurrent wall.
2. P0 — OS scheduling/stack/wait для реально пойманного эпизода. Сохранять
   unsupported/access failure явно. Без этих данных prepare wall−CPU
   не доказывает ожидание драйвера, mutex или свободный CPU.
3. P0 — GPU query frames и queue/fence evidence с тем же source ID.
   Настоящий submit/present отдельно от tail, latest GPU samples не
   приписывать текущему CPU кадру. Качество картинки сохранять.
4. P0 — после наблюдаемости сокращать главный синхронный sim/render путь:
   отдельный владелец симуляции, bounded commands/presentation, проверка
   30 Гц, replay, reset, задержки приказа и сохранения всех эффектов.
5. P1 — фиксированный workload, повторные ordinary пары и контроль overhead
   оборудования записи; сравнивать одинаковые steps/hash/counts, а не
   разное состояние на последней стеновой секунде. Длинные camera/reset
   сценарии и tail cost/memory оставлять отдельно от среднего FPS.

WBPERF-001 частично продвинута; WBPERF-002/026/027 и 165 FPS остаются открыты.
