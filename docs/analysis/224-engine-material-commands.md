# Прочность и плавление материалов через общий движок

Дата: 08.10.2026. Продолжение EP-02a/02b после
[223](223-engine-debris-commands.md), контроль — frozen 223.

## Исправление и его граница

Панель напрямую вызывала `Registry::replace` для прочности, порога
плавления и плотности. Первые два свойства теперь меняются через
`Command::TuneMaterial { material, field, value }`: явный ID материала,
`MaterialField::Strength = 0` / `Melt = 1`, целочисленное значение.
Это общий обработчик для материалов исходного набора мира; названия
сценариев, виды юнитов и ID из панели не участвуют в выборе алгоритма.

Нормализация прежняя: Strength снизу ограничивается 1, Melt принимает u32.
Проверка Registry остаётся авторитетной: Strength выше MAX_STRENGTH,
попытка назначить прочность воздуху и отсутствующий материал дают Rejected;
тот же допустимый результат даёт Unchanged. Обработчик записывает один
Outcome. CommandRuntime вызывает его через прежние очередь, порядок и
бюджет. Portable checkpoint v1 получает tag4: u64 адрес материала, u8
поле, u32 значение. Адрес шире u16 и неизвестное поле отклоняются;
существующие tags и conformance bytes не меняются.

Панель переводит на команды все восемь строк прочности и две строки
плавления. Округление, диапазоны, reset и generation overrides прежние.
Плотность пока остаётся прежним прямым writer: этот пакет **не завершает
миграцию всего реестра** и не исправляет её связь с учётом материи.

## Применённое состояние и формат

Physical snapshot56 выбирается только при изменении Strength/Melt
относительно исходного набора материалов. Перед физическими разделами
записывается разреженный префикс: u32 число материалов, затем в порядке
ID — u16 ID, u8 маска двух свойств и изменённые u32 значения.
После него идёт строгий bool наличия конфигурации Blast, её префикс
из snapshot55 при необходимости и строгий bool хвоста ходовой.
Все зависимые свойства восстанавливаются до физических загрузчиков;
прежние обязательные хвосты 49/52/53 записываются и при пустом состоянии.

Читатель отклоняет пустой/слишком большой список, отсутствующий ID,
повторы или нарушение порядка, неизвестные биты, записанные defaults,
недопустимую прочность, неверные bool и обрезанные данные. Форматы 27…55
по-прежнему читаются. Нетронутые миры и миры только с настройками ходовой
или обломков сохраняют прежние bytes/hash. Возврат этих двух свойств к
defaults убирает новый формат. Старые executable не читают snapshot56.

Registry предоставляет read-only обход definitions в порядке явных ID,
пропуская дыры. Defaults захватываются один раз при построении мира;
команда не разрешает динамически добавленный после этого материал,
поскольку добавление набора ещё не имеет snapshot-контракта. Для stock
набора это 10 записей `(u16, [u32; 2])`; один Vec и 120 bytes элементов
с выравниванием (capacity может быть больше), без копирования геометрии. Команда делает
binary search по defaults и прямой доступ к Registry, без обхода
корпусов, обломков или ledger. Сравнение/кодирование свойств выполняется
при snapshot/hash, не в обычном физическом тике.

## Почему плотность требует отдельного исправления

`Matter::new` создаёт Body containers как число оставшихся клеток,
умноженное на `Economy::per_voxel(3)`. `Matter::load` проверяет то же
равенство у корпусов, а у обломков — `count * per_voxel(material)`.
Прежний density setter меняет Registry, но не уже записанные количества.
В `step_sections_in` и `annihilate_body` требуемый перевод/сток снова
считается по текущей плотности и проверяется assert_eq. Поэтому сохранение
новой плотности без перехода учёта может отклонить собственный снимок;
при разрушении корпуса возможно несовпадение требуемого и доступного
количества. Сброс плотности при restore тоже не является исправлением:
он теряет настройку, а обломки могут уже иметь другую стоимость.

Следующий density этап должен определить согласованную семантику для
существующей материи, новых claims, тел, фрагментов и накопленных стоков.
Нужны проверки изменения до/во время боя, повторного изменения/reset,
частично выполненных попаданий и sections, сохранения до/после команды,
баланса и отсутствия скрытого уничтожения/создания материи. Простое
ослабление loader, подмена initial ledger или сброс мира не доказывают
корректность. До такого исправления прежний density writer и его риск
остаются открытыми в EP-02/03.

## Приёмка

До замеров записан `out/engine-fixes-20261008/material-commands/acceptance.json`.
Проверяются старые setter semantics, все поля команды в runtime hash,
pending portable restore, комбинации material/motion/debris и возврат
к прежним байтам. 240-тиковый бой сравнивает прежние прямые изменения,
CommandRuntime и загруженную копию на каждом тике; требуется реальный
огонь, обломки и сохранение баланса. UI проверяет все десять строк,
числовой ввод, reset и пересоздание на прежнем тике.

Stock бой — 3600 ticks, совпадение всех 25 нетайминговых полей, исхода
и hash с frozen 223, late restore 3300→3600. Одна ordinary native пара
по 120 секунд проверяет регрессию: FPS не ниже 97% контроля, p99 не выше
103%, valid/eligible, темп и hash прежние. Это не серия для доказательства
ускорения. Тесты и сборка не совмещаются с замерами.

Целевой прогон material_ — 12 pass. Полный release-прогон sim-core/nav/modding
— **966 pass, 0 fail, 6 ignored**: 913 проверок симуляции/навигации и 53
проверки данных. В симуляции добавлено шесть регрессий относительно 223.
Architecture — 5 pass / 4 fail, те же 46 нормализованных диагностик,
без добавлений. Остаются render writes, floats, hash containers и clock.
`rustfmt --check` затронутых файлов и `git diff --check` проходят.
Golden/conformance файлы не менялись.

Полный blast suite — **152 pass, 0 fail, 4 ignored**, включая две новые
проверки панели. Кнопки всех десяти строк дают ровно по одной команде;
reset восстанавливает реестр, плотность не меняется. Ввод прочности стали
999999 ограничивается UI до 5000 и после rebuild0→0 применяется ровно
один раз через тот же вход. Старые тесты не ослаблялись и не переписывались.

Три последовательных headless боя по 3600 тиков, 60 юнитов, 8 physics /
8 navigation workers: frozen 223 control, кандидат, кандидат с late restore
3300→3600. Совпали **25 нетайминговых полей каждого тика**, shots/damage,
alive [26,21], базы [100,100], peak_rounds=30 и hash **`5dd0c782d2b2f557`**.
Восстановление прошло. Mean step: **13,402 / 13,491 / 13,480 мс**
соответственно. Ускорение не показано; этот небольшой ряд не устанавливает
причину разницы. Изменённые свойства и pending команды проверены отдельно
в 240-тиковом бою, а эти прогоны проверяют сохранность stock пути.

## Игровое окно

Одна ordinary пара world-battle по 120 секунд, control → кандидат,
1600×900, AutoNoVsync, 8 physics / 8 navigation / 4 compute workers.
Настройки закрыты, GPU/core trace не включён. Ввод панели проверен
отдельными тестами; эта пара проверяет обычный бой.

| Mean FPS | 71,8 | 71,6 |

| p99 кадра, мс | 33,128 | 33,320 |
| Max кадра, мс | 52,304 | 57,928 |

FPS −0,28%, p99 +0,58%: записанный заранее допуск 3% пройден. Оба
профиля valid/eligible, выполняют 3600 ticks/120 s, сохраняют исход и
hash `5dd0c782d2b2f557`. `--require-valid` и `qualification.json`
подтверждают приёмку и паспорта сборок. **Ускорение не показано, 165 FPS
не достигнуты.** Max кадра вырос на 5,624 мс; одна пара не устанавливает
причину разброса и не подтверждает улучшение редких задержек.
