# Обзор наблюдаемости: реальные render-вызовы и объём работы — ADR-542

03.10.2026, исходный main `f043fdd`. Сценарий: бой ИИ против ИИ 30×30
на километровой карте, штатное качество, 1600×900, RTX 5090 / Vulkan,
физика/навигация 8/8. Цель остаётся 165 FPS при авторитетных 30 Гц.
Этот этап исправляет диагностику, не заявляет достижения FPS или причины
редкого многосекундного зависания.

## Что дают предыдущие оптимизации

| Подход | Что подтверждено | Чего результат не доказывает |
|---|---|---|
| Устранение повторных запросов мира/опор, независимые задания в постоянном пуле с упорядоченным commit, 527/528 | Сокращён объём полезной работы, сохранён детерминизм | Равномерная загрузка CPU и свободный от симуляции render frame ещё не обеспечены |
| Постоянные render-слоты и отсутствие пустых Transform writes, 531 | Убрана повторная работа ECS и пересоздание объектов | Фризы и цель 165 FPS остаются |
| Малые индексы, маски и изменение размера Rayon jobs, 529/532/534 | Измерения CPU отдельных участков иногда улучшались | Устойчивого выигрыша всего боя не было; плохие варианты откатили |
| Быстрые таблицы ID обломков, 536 | Fragments-группа дешевле, два допустимых сочетания показали лучший FPS | Оба сочетания используют один контроль; это не две независимые пары, большие паузы остались |
| Phase-ring и frame-trigger с поздним резервом, 535/540 | Паузы главного кадра сохраняются вместе с доступным контекстом | Непокрытые эпизоды не объясняет тихий хвост; число окон ограничено |
| Source-frame timeline, 541 | Main и CPU-render имеют общий epoch и неизменную идентичность кадра | Широкий интервал prepare не был временем конкретного gas job; CPU ведущего потока не включал воркеры |

Общий процент загрузки CPU не является достаточной метрикой. Один
последовательный тик переходит между Bevy Compute-потоками. Новая трасса
наблюдает четыре таких OS ID: у них есть и tick_caller, и реальные gas jobs.
Это не четыре одновременно работающих тика. На весь процесс в длинных
прогонах приходится около 2,56 эквивалента ядра. Этот показатель не
различает полезную работу, конкуренцию за общий пул, ожидание результата,
preemption или драйвер.

## Что мешало понять причину и что исправлено

1. `render_prepare` объединял много систем Bevy и промежутки расписания.
   Новый scope `gas_prepare` находится непосредственно внутри функции,
   а его CPU/cycles принадлежат фактически вызвавшему её потоку.
2. Аналогично `gas_extract` записывается внутри `ExtractResource`, а не
   выдаёт последний атомарный замер за новую работу каждого кадра.
3. Prepare разбит на реальные синхронные участки: `gas_views_uniform`,
   `gas_terrain_upload`, `gas_bricks`, `gas_regions`. Scope guards сохраняют
   нормальное завершение или ранний выход; отсечение записи оставляет span
   открытым. Длительность неполного вызова не заменяется нулём; workload
   завершается вместе с successful scope, aborted counters не являются
   доказательством выполненного нулевого объёма работы.
4. Вместе с вызовом сохраняются patches/words/distant_words, число регионов,
   созданных GPU-регионов и отправленных deposits. Явные terrain/distant
   `queue.write_buffer` и `queue.submit` имеют число вызовов и байтов.
   Это не все GPU-загрузки: uniforms, masks и остальные системы сюда не
   входят. Сумма transfer counters берётся только с upload leaf, без
   повторного сложения родителя и его детей. Deposits в extract/views —
   входные записи, в regions/prepare — фактически добавленные GPU deposits.
5. Идентичность потребляющего кадра отделена от `input_frame_row` — кадра,
   в котором был извлечён payload. Bevy извлекает ресурс по change detection.
   Диагностическая метка устанавливается через `bypass_change_detection`:
   она сама не заставляет повторно копировать неизменные данные. При
   переиспользовании payload extraction span отсутствует, а прежний source
   ID остаётся прежним. Доизмерительный payload имеет неизвестный ID.
6. Удалён `PROFILE_RENDER_PREPARE` через stderr на горячем пути: он печатался
   именно при медленной подготовке и мог искажать измерение. Прежние latest
   atomics/peak summary сохранены, но не заменяют новую привязанную трассу.
7. Markdown показывает actual extract и prepare в отдельных рейтингах,
   объём работы и calling-thread CPU. Исправлена отсутствующая колонка CPU
   в прежнем заголовке таблицы. Широкий prepare отдельно показывает время
   вне gas call; огромный словарь всех вложенных workload больше не
   скрывает основной результат.

Render trace schema 2 читается вместе с прежней schema 1, но разные
контракты не образуют равную пару. Parser проверяет колонки/status, identity,
clocks/cutoff, bounds/nesting, одинаковый поток синхронных детей и порядок
участков. Extract/prepare могут исполняться на другом потоке относительно
родительского schedule. Без drops ссылка на payload обязана иметь реальное
извлечение и совпадающие неизменные facts patches/words/regions.

Сохраняется лимит 100000 spans и запись в память с выгрузкой после замера.
Короткий mutex recorder и дополнительные counters имеют диагностическую
стоимость. Новых зависимостей между отдельными prepare jobs нет; обычный
режим не устанавливает профильный plugin. Физика, частота симуляции,
качество, поля и upload acknowledgement не менялись.

## Нативная проверка

Замороженный `out/fix542/blast.exe`, SHA256:
`b90cf4d46af6c1048d5383a9462239a5e424a18bc24976a813603bb746d46fe4`.
Сборка содержит те же отдельно подготовленные изменения ADR-523,
что и предшествующий замер: это не чистый snapshot Git. SHA идентифицирует
exe, а manifest SourceAtLaunch не доказывает его происхождение.
Запуски последовательны, без сборок/тестов/правок/видео во время замера.
Фокус, размер окна и render context проверены. Все четыре offline анализа
прошли `--require-valid`; raw CSV, manifests, CPU samples, logs и exe

В этих сценах GasInput фактически изменялся каждый кадр, reused payload
calls = 0. Переиспользование проверено отдельно Rust/Python regression
fixtures; нативный прогон не выдаётся за покрытие этого случая.

Обычный и диагностический бой имеют разные шаги/состояния. Один прогон
каждого режима не доказывает нулевой overhead или ускорение после удаления
stderr. Обычный режим тоже не выдерживает реальное время; 165 FPS открыты.

## Что теперь стало видно

**Газовая подготовка не объясняет весь prepare.** Source row 7201,
generation 0, tick 3248: render_prepare 39,0085 мс, реальный gas_prepare
1,2151 мс, root graph 2,4597 мс. Остальные 37,7934 мс находятся вне gas
call. Это другие jobs/расписание/ожидания, пока без установленной причины.
Максимум gas_prepare за весь бой — 4,1965 мс, row 6258; его CPU time delta
0 при 4 243 670 cycles. Ноль coarse Windows counter не означает idle.

**Извлечение данных имеет отдельную значимую цену.** Source row 7174,
tick 3221: actual gas_extract 22,7336 мс, calling-thread CPU 15,625 мс,
94 916 050 cycles, 34305 выходных patches / 184943 words / 8 regions.
В row 7201 этот вызов занимает 20,7665 мс при extract callback 21,7494 мс.
В отличие от CPU ведущего callback, CPU самого job показывает активную
работу. Но функция включает clone/sort/merge dirty ranges, упаковку слов
и clone atmosphere/distant metadata: нельзя назвать всю цену чистой
копией байтов или вывести причину только из числа выходных патчей.
Отдельные фазы и количество исходных unmerged dirty ranges пока не
записаны. Это следующий конкретный пробел WBPERF-007/008.

**Actions выделяет другую нагрузку.** В row 3804, generation 4, tick 48:
gas_prepare 6,5770 мс, почти всё в terrain upload 6,5654 мс. Там 21 явная
запись / 88080384 байта distant terrain. Общий render-system boundary
17,0099 мс имеет tail 14,5912 мс. Эти вложенные интервалы не складываются;
tail не доказывает чистое время present или GPU execution.

**Критический путь симуляции остаётся.** Средний core за реальный шаг
15,4381 мс в diagnostic и 15,2813 мс в ordinary. Максимальный frame interval
109,1445 мс следует за срезом 93,2777 мс/core 82,9873 мс и gap 15,8668 мс.
Разбор рендера не превращает эту последовательную Update-цепочку в
независимую симуляцию. Редкий прежний core-пик 500…750 мс не воспроизведён,
и причина его остаётся неизвестной.

Windows thread CPU грубый: delta иногда превышает wall, иногда равна нулю.
Нельзя clamp-ить это в «lock wait», складывать вложенные counters или
переводить cycles в миллисекунды. JSON сохраняет исходные значения.
