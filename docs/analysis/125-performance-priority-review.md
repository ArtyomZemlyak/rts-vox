# Повторный обзор производительности боя, 03.10.2026

Исходный HEAD: `23f894f` (ADR-530). Сценарий: бой ИИ против ИИ на всей
карте 1 км, 30×30 юнитов, все штатные шасси/оружия, физика и эффекты.
Цель: 165 FPS, бюджет кадра 6,061 мс, симуляция 30 Гц без замедления.
Локальные ранее подготовленные изменения остаются в рабочем дереве;
измеряемые бинарники идентифицируются SHA-256, а не только Git HEAD.

## Что изменилось в понимании проблемы

Начальные цифры аудита [118](118-world-battle-performance-backlog.md),
включая 1,3 FPS и тик 90 мс, — история старого состояния. Их нельзя
использовать для текущей расстановки приоритетов. Последние три обычные
пары ADR-530 дают примерно 90–96 FPS и 11,6–11,9 мс core на реальный
тик. 30 Гц соблюдаются. Диагностические профили с worker scopes отдельно:
они дороже обычной игры и не являются эталоном FPS.

Подтверждённый главный дефект: `advance` выполняет авторитетный тик внутри
последовательной цепочки Update. Рендер ждёт завершения тика, публикации
занятости и подготовки картинки. Тик в среднем уже почти вдвое длиннее
бюджета кадра, хотя до бюджета симуляции 33,333 мс ещё есть запас.
Догоняющий пакет ограничен, но его первый дорогой тик всё равно блокирует
кадр. Разгонять только число worker threads это не исправляет.

В трёх обычных after-прогонах ADR-530 средний расход на один render frame:

| Участок | мс/кадр | Сумма за минутный бой | Ограничение интерпретации |
|---|---:|---:|---|
| Авторитетный core | 3,65–3,66 | 21,0 с | Выполняется примерно в 30% кадров; 11,6–11,7 мс/тик |
| Группа `fragments` | 1,85–1,87 | 10,6–10,7 с | Это `moving::animate` + `fragments::draw` + `bodies::draw`, не только обломки |
| Занятость юнитов для изображения | 0,94–0,96 | 5,4–5,5 с | Вложена в terrain/input, не складывать с ними повторно |
| Прочая presentation-группа | 0,72 | 4,1–4,2 с | Не включает ожидание GPU вне измеренных границ |
| Мешинг юнитов | 0,04 | 0,22–0,24 с | Не главный постоянный расход сейчас |

В обычном CPU-стенде движение около 4,0–4,1 мс/тик, обломки 2,3–2,4,
rubble 0,5–0,6, тепло суммарно около 1,3. Поздний бой дороже раннего:
тик 5,5 → 14,2 мс, движение 2,5 → 5,1, обломки 0,8 → 3,3;
это окна по 300 тиков одного baseline-прогона, не прогноз бесконечного боя.
Решения ИИ занимают около 3–9 мкс/тик. Переписывать правила ИИ ради FPS
сейчас малоэффективно; движение его юнитов входит в дорогую motion-фазу.

| 5 | Повторная физическая индексация обломков и опор | P1, ~2,4 мс/тик debris + ~0,5 rubble; растёт в позднем бою | Обрабатывать активные изменения, укрупнять слишком мелкие задачи; проверять обычный native, а не только CPU (WBPERF-005/011) |
| 6 | Нагрев и волны оружия | P1, тепло ~1,3 мс/тик; волны ~1 мс/тик, отдельные большие старты поиска | Инкрементальные пакеты и контроль одновременной работы без урезания урона/частоты симуляции (WBPERF-010/012/017) |
| 7 | Камера, streaming, reset, GPU-газ | P1, отдельные пользовательские зависания; нынешний статичный world-battle не даёт полного покрытия | Actions/движение камеры/длинный reset и GPU timeline при прежнем качестве (WBPERF-009/014/023) |
| 8 | Правила выбора целей ИИ, UI, низкоуровневые микрофиксы | P2 по текущему расходу; решения ИИ в микросекундах, UI не доминирует в этом сценарии | Возвращаться после критического пути либо при новом воспроизведении (WBPERF-020/022/025) |

Средняя загрузка CPU примерно на 2,6–2,7 эквивалента ядра сама по себе не
доказывает недостаточную параллельность или простой конкретного пула:
в ней смешаны рендер, ожидания и работа симуляции с частотой 30 Гц.
Нужны реальный параллельный критический путь и меньший объём работы,
а не цель загрузить весь CPU. Worker job totals пересекаются и не суммируются
с временем родительских фаз. GPU ещё может ограничить уже ускоренный кадр.

## Первый фикс в критическом пути: постоянные render-объекты обломков

`fragments::draw` каждый кадр создавал два `BTreeMap` по всем физическим
кускам, заново вычислял их матрицы/кватернионы и записывал Transform даже
для лежащего завала. Это заставляло downstream Bevy заново обрабатывать
неизменившиеся объекты. При ~23 тыс. кусков такой расход повторяется на
частоте кадров, а не 30 Гц симуляции. Значение ~1,86 мс относится ко всей
группе; собственное время этой функции пока отдельно не измерено.

Исправление: постоянная таблица ID→entity, сравнение физической позы,
пересчёт поворота/масштаба только при её изменении. Предыдущая позиция и
alpha остаются текущими на каждом кадре, поэтому полёт, приземление и
пауза сохраняют прежнюю интерполяцию. Неизменившийся Transform не записывается.
Удалённые куски освобождают entity и handles секции; внешнее удаление
entity восстанавливается. Повторное использование ID с другой формой,
материалом/покраской теперь корректно пересоздаёт mesh. Физический список,
дальность, качество эффектов, пулы и тактовая частота не меняются.

Это первый компонент WBPERF-002/013, а не независимая симуляция и не
закрытие 165 FPS.

## Проверки и границы первого фикса

Полный набор blast render-тестов до добавления финальной lifecycle-проверки:
88 прошли, 2 ignored. На финальном исходнике семь fragment-тестов прошли,
включая шесть новых: reuse неподвижных объектов без Changed<Transform>,
интерполяция полёта/приземления, пауза, изменение позы/размера без смены
тика, reset со сменой mesh/material и повторным ID, внешнее удаление,
очистка entities. Существующий тест геометрии насыщенного завала — из ранее

## Архитектурный следующий шаг

Отдельный поток единолично владеет авторитетным миром. Сначала выделить
читаемый presentation-контракт из многочисленных прямых `Scene.sim` reads
и команд из UI; не переносить весь мир каждый кадр через `snapshot()`.
Затем bounded-публикация поз/ревизий с отдельным сохраняемым журналом
попаданий, смертей и terrain edits. Команды несут sequence/tick/generation;
restart отменяет старое поколение. Интерполяция читает только завершённые
снимки, никакого блокирующего `join`/mutex на кадре. Проверка: replay на
1/2/4/8 workers, 30 Гц в позднем бою, задержка приказа, reset/камеры,
ограничение памяти и одинаковое количество разрушений/эффектов.

Это главный оставшийся архитектурный пункт. Запуск `sim.step` в scoped
worker с ожиданием в том же кадре либо копирование всего мира создадут
видимость параллелизации и сохранят основную проблему.
