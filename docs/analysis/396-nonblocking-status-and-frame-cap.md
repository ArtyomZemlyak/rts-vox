# Вывод статуса без задержки тика и потолок200 FPS

24 октября2026. Продолжение394 и прерванного профилирования395.
Артефакты: `out/optimization-396`, исходные журналы — `out/profiling-395`.

## Основание

Из ранее собранного `gpu-render/world-battle.csv` вычислен остаток
`simulation_input_ms - physics_ms - terrain_ms - atmosphere_ms` для
кадров с ровно одним тиком. Это не отдельный измеренный scope и не CPU
time: туда входят прочая работа, вывод и возможное вытеснение потока.
Пять остатков больше10мс пришлись на тики, кратные30; максимум56,2354мс
на1170. Среди1740 остальных тиков таких случаев нет, медиана0,1119мс.
В ordinary-a/b медианы на каждом30-м тике0,7151/0,7174мс против
0,0719/0,0728мс на остальных. Остатков больше10мс в этих ordinary нет.
Сводка сохранена в `periodic-status-evidence.json`.

В конце `advance` именно каждые30 тиков выполнялся синхронный
`println!` со статусом. Связь по времени сильная, но без scope/OS-стека
нельзя приписывать весь остаток stdout. Исправляется конкретный
блокирующий путь; устранение всех пиков или рост FPS не предполагаются.

## Изменение

`status_log.rs` передаёт только небольшую запись с числами в bounded
канал на8 сообщений. Форматирование и запись stdout выполняются
отдельным потоком `runtime-status`. Горячий путь использует `try_send`:
при заполнении очереди/обрыве приёмника необязательный статус пропускается.
Число пропусков выводится с очередной принятой записью и в итоговом
`PROFILE runtime_status_dropped`. Записи о единственном попадании из
`advance` проходят через тот же канал. CSV, состояние SIM и события
повреждений от этого канала не зависят.

При закрытии приложения нет ожидания заблокированного stdout. Последние
строки статуса являются best effort и могут не успеть выйти до завершения
процесса. Полные журналы профиля пишутся прежним отдельным путём.

По просьбе пользователя обычная игра и runner получают потолок200 FPS.
`--fps-limit N` / `-FpsLimit N` задают потолок;0 явно отключает его.
`frame_limit.rs` ждёт оставшуюся часть периода через `thread::sleep`
в First перед обновлением Time. Следующий срок считается от фактического
начала кадра: после тяжёлого кадра нет догоняющей серии. Планировщик OS
может увеличить ожидание; это потолок, а не обещание постоянных200 FPS.
Симуляция сохраняет свою частоту и накопитель времени. Размер куба,
квоты, повреждения, маршрутизация и скорость юнитов не меняются.

Runner сохраняет потолок в manifest и требует подтверждения
`PROFILE fps_limit=N` в stdout. Сравнение разных потолков или способов
запуска окна отвергается; старые manifests без потолка считаются
uncapped. Новому runner для запуска требуется бинарник с `--fps-limit`.
`TargetFps` остаётся критерием приёмки, отдельным от потолка.

## Проверки

- Четыре изолированных Rust-теста status_log: заблокированный writer не
  удерживает producer/Drop; ограниченная очередь сохраняет порядок;
  обрыв/отключение только считают потери; формат и marker пропусков точны.
- Два изолированных теста frame_limit: остаток5-мс периода, отсутствие
  ожидания после долгого кадра/на первом кадре, новый срок и отключение.
- `cargo check -p render --bin blast -j1` до добавления ограничителя
  прошёл за10,35с. Финальный код проверяется release-сборкой ниже.
-139 Python-тестов анализатора и PowerShell suite profile tools прошли.
  Проверены потолок, LaunchWindowStyle и отдельная приёмка Background.

## Фокус окна и фоновая диагностика

Пользователь уточнил, что основная помеха — перехват фокуса окном.
Одного Start-Process Hidden недостаточно: Bevy по умолчанию создаёт
активное окно; кроме того, pinned winit на Windows вызывает SW_MAXIMIZE,
который может активировать даже окно с with_active(false).

Runner теперь по умолчанию передаёт `--profile-background`. Окно
создаётся с focused=false, AlwaysOnBottom, без нативного maximize;
размер клиента задаётся явно. WinitSettings continuous позволяет
собирать фоновую трассу без искусственного unfocused лимита60Гц,
потолок200 FPS при этом сохраняется. Активирующий Start-Process или
Maximized без явного `-Foreground` отвергается до запуска процесса.
Обычный ручной запуск игры сохраняет интерактивное окно.

Background фиксируется в manifest и подтверждается логом. Фоновая
диагностика сохраняет исходные данные и возможность сравнения с такой
же фоновой диагностикой; её FPS не проходит ordinary приёмку и не
смешивается с foreground. Трассировка остаётся доступной с CorePhases/
RenderTimeline и прочими явными флагами, без необходимости перехватывать
фокус.

Пятисекундный smoke после финальной сборки прошёл:100 тиков, клиент
3840×1949, focused=false и render_context_changed=false, ограничитель200,
runtime_status_dropped=0. Hash `562ca53ed56eec31`, core CSV7370797байт.
Офлайн-анализ подтвердил100/100 трассированных тиков, valid=true,
fps_eligible=false, realtime=true, reasons=[]; таймлайн не экспортировался.
Это проверка работы фонового захвата, а не поздних пиков длительного боя.
Процесс завершился штатно. Итоговый binary SHA256:
`499BAE46DA6D8C2282A35D2FABAA21BCCAB2167E42B217CD81F326D6E6152B40`.
Обновлены target/release/blast.exe и соответствующая build metadata;
предыдущие сведения сохранены в каталоге артефактов.

Пример короткой фоновой трассы без активации:

```powershell

```

Активация/нативный maximize в этом режиме не запрашиваются. Проверен
также отказ `-Maximized` без `-Foreground`: до создания output/process.
