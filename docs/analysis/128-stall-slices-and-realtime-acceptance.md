# Долгие тики обычного боя и приёмка без потери времени — ADR-534

Дата: 03.10.2026. Продолжение [127](127-laser-and-thermal-worker-observability.md).

## Принятое исправление

Обычный профиль уже измерял begin/end главного Update и core wall каждого
вызова симуляции, но отчёт не показывал разбивку самых долгих Update-срезов
и последовательности зависаний без подробной worker-трассы. Анализатор
теперь выводит `slow_slices`, `slice_summary` и `stall_episodes` в JSON/Markdown.

У каждого среза есть поколение, диапазон тиков, количество шагов, собственный
wall, core wall, четыре последовательные Update-фазы, вложенные детали,
следующий begin-to-begin интервал и следующий межсрезовый промежуток.
Интервал в строке N включает работу строки N−1; прежняя корректная таблица
previous/current сохранена. Новый разбор явно связывает срез с последующим
интервалом, чтобы не объяснять зависание работой следующего кадра.

`single_tick_ms` доступен только при одном шаге в срезе. Для нескольких
шагов сохраняются сумма и среднее, без выдуманных стоимостей отдельных
тиков. Эпизоды объединяют соседние срезы с собственным wall ≥50 мс либо
следующим промежутком ≥50 мс; смена поколения разрывает эпизод. Срезы и
следующие промежутки не перекрываются. Последний срез сохраняет собственный
wall, но не получает несуществующий следующий интервал. Подробности
ограничены `--top`; полный счётчик эпизодов и статистика остаются полными.

Core/occupancy/physics/terrain/atmosphere — вложенные детали. Их нельзя
складывать с четырьмя Update-фазами. Render prepare/extract — последние
асинхронные атомарные наблюдения: одно значение может повторяться много
строк. Их среднее/сумма по строкам не измеряет работу render thread. Они
исключены из новой разбивки; raw CSV и прежние значения сохранены.

Исправлена приёмка замедленной симуляции. PowerShell `AcceptanceEligible`
теперь требует также `MeetsSimulationRate`. Python независимо пересчитывает
этот критерий из фактических шагов, монотонного конца окна и tick rate,
показывает `acceptance_eligible` и отвергает пару с замедлением world-battle,
даже если обе стороны имеют одинаковые число шагов и хеш. Старый критерий
темпа сохранён: не меньше floor(seconds × rate)−1 шагов. Данные остаются
валидными для диагностики; потеря времени не маскируется как ускорение.
`profile-range.ps1` уже требовал этот темп в MeetsP99/MeetsEveryFrame; исправлены
отдельный флаг и gate анализатора, а не объявлено, что прежний CheckBudget
принимал такие результаты. Аналитический JSON schema 4; runtime CSV,
manifest schema 2 и core trace schema 3 не изменены.

## Эксперименты с occupancy отклонены

Первый прототип пропускал целый raster при неизменных входах. Проверка
call sites показала, что он вызывается после тика/смены окна/reset, а не
каждый кадр. Поэтому польза в активном бою ограничена. Средний occupancy
в frame CSV — стоимость, взвешенная кадрами без тика, а не цена одного raster.
Этот прототип не участвовал в нативном A/B; сохранён в
`out/performance/fix534-rejected-whole-raster/`.

Второй прототип разделял world-cell кеш по нижнему корпусу, башне и
сегментам. Проверки точных ячеек, packed GPU shadows, column tops, dirty
spans, revision, camera clips, damage, reset, разных worker counts прошли.
Полный render suite: 92 passed / 2 ignored; clippy без новых предупреждений.
Однако три нативные пары не прошли строгий workload gate. Убедительного
ускорения не установлено; код полностью откатили, тесты и исходники
сохранены в `out/performance/fix534-rejected-section-cache/`. Никакого
упрощения картинки или физики не принято.

## Шесть обычных нативных прогонов

Стоковый world-battle AI-vs-AI, 60 секунд, окно 1600×900, RTX 5090 Vulkan,
physics/navigation 8/8, цель 165 FPS. Последовательный порядок:
before1, after1, after2, before2, before3, after3. Без CorePhases/CpuThreads,
GPU timestamps, конкурирующих сборок/тестов и изменений исходников.

Обе сборки содержали одинаковые ранее подготовленные локальные изменения
за пределами этого исправления. Это сравнение замороженных рабочих сборок,
не двух чистых коммитов. До: `blast-fix533-after-v2.exe`, SHA256
`cef9aaebbf80f1dcf9f3596f8815945bfd5489312b2a410db601e75a963ac71d`.
Отклонённый after: `blast-fix534-after.exe`, SHA256
`2f79ca6a2901849bc6ca9630a4bcc6bc0aab0505010277a43b0fb5fe4db6f82b`.
Запускаемый `target/release/blast.exe` восстановлен из before и проверен по SHA.

Raw manifests неизменны; новый Python gate пересчитывает пригодность,
поэтому старый AcceptanceEligible=true при замедлении не является приёмкой.

## Что показали зависания

В before3 основной эпизод: строки 3656…3667, тики 865…876, 12 срезов.
Собственный Update wall 3114,613 мс, core wall 2974,195 мс, следующие
промежутки 242,169 мс; неперекрывающийся охват 3356,782 мс.

Самый долгий срез — строка 3663, тик 872: Update 759,793 мс, core
750,752 мс; следующий наблюдаемый интервал в строке 3664 — 789,068 мс,
следующий промежуток 29,275 мс. Вложенный occupancy здесь 3,300 мс.
Это привязывает основную часть wall к вызову симуляции, а не доказывает
GPU/lock wait, загрузку CPU или виновность какой-либо worker-фазы.

В after2 эпизод строк 5078…5086, тики 1546…1554: 9 срезов,
Update 1840,836 мс, core 1645,341 мс, промежутки 180,738 мс,
охват 2021,574 мс. Тик 1552 — core 294,112 мс; его следующий
наблюдаемый интервал 310,652 мс. Паузы встречаются в обеих версиях.
Обычные прогоны не содержат внутреннюю worker-трассу этих эпизодов,
поэтому причины пока неизвестны.

## Проверки и следующий приоритет

39 Python regression tests и 16 PowerShell validity/timing/context cases
прошли. Проверены ordinary без core.csv, правильный следующий интервал,
вложенные/асинхронные метрики, multi-step, wrap тика, смена поколения,
последний срез, bounded detail, legacy unavailable и две одинаково
замедленные стороны. Переразбор всех шести raw runs сохранил FPS/шаги/хеши;
минутный ADR-533 diagnostic/1801 trace также проходит проверку целостности.
Нативную сборку под принятый фикс не делали: он меняет только offline
инструменты, физика и renderer восстановлены.

WBPERF-027 теперь приоритетнее мелких occupancy правок: нужен trigger/ring
trace вокруг длинного core-вызова с полным worker coverage и OS
scheduling/stack/wait, затем исправление подтверждённой причины и soak.
Синхронный sim/render остаётся WBPERF-002; обычный core около 12,3 мс
против бюджета кадра 6,061 мс. 165 FPS, редкие паузы и потеря времени
симуляции остаются открытыми. Этот ADR исправляет диагностику и ложную
пригодность сравнения, не объявляет ускорение или устранение зависаний.
