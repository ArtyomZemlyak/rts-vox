# Групповое движение и соседние машины — 15–16.10.2026

Исходный main: ee7995d. ADR-724. Проверяются общие механизмы SIM,
а не отдельный обработчик боя с ИИ. Все заезды CPU-only, без оружия,
рендера и разрушения: эти числа не являются FPS полноэкранной игры.
Артефакты локально: out/crowd-20261015/.

## Найденные причины

1. UI назначал места по порядку выделения, с фиксированным шагом 90 клеток
   и сеткой вдоль мировых осей. Для 10 танков из 3 продольных рядов по 4
   получались 4 продольных ряда по 3: машины пересекали пути друг друга.
2. Размеры корпуса не участвовали в расстановке: шаг для танка применялся
   к большому пауку. Крайние места отдельно clamp-ились к границе,
   что могло объединить несколько назначений в одну точку.
3. Более быстрый следующий танк доезжал до коллизии с медленным ведущим.
   Отказ включал новый поиск, передачу контактного импульса и recovery.
   Простая очередь превращалась в объезды и движение задним ходом.
4. Точный SAT контакта повторял тригонометрию даже для удалённых пар.
5. Сложный встречный разъезд и слияние в ворота остаются отдельной проблемой
   локального планирования: исправление назначения строя само их не решает.

## Что изменено

Формирование мест перенесено в BlastRange. Ограниченный набор выбирается
из живых союзных мобильных акторов; дубликаты/неверные ID не создают места.
Шаг — округлённый вверх диаметр окружности корпуса плюс удвоенную сумму
cell_units и plan_margin. Большая машина увеличивает шаг всей группы.
Для танка шаг 88 клеток
(8.8 м), запас каждой стороны — cell_units + plan_margin. С одним общим
запасом 10 танков проходили, но диагональный строй 64 ловил контакты;
раздельный запас соседних машин дал 64/64 без контактов.
Широкая сторона сетки поперёк главного направления движения.
Целочисленный Hungarian минимизирует сумму квадратов расстояний;
ничьи стабильны по ID и месту. Работа O(n³) однократно на приказ, n<=64.
Сетка целиком переводится внутрь карты; невмещаемая группа не получает
совпадающие/внемировые места. Существующие FormationMove с явными целями
остаются входом исполнителя и диагностического replay.

Перед движением создаётся неизменяемый снимок соседей. На прямом финальном
участке маршрута следующий корпус ограничивает скорость по зазору и
продольной скорости ведущего, с общей дискретной формулой торможения.
Ожидающий начальный маршрут ведущий также учитывается. Поворот, partial
route, реальный блок, погибшая/обездвиженная или завершившая приказ
машина и escape сохраняют обычное локальное планирование. Совет не редактирует маршрут,
не телепортирует и не заменяет точный допуск корпуса/грунта.
Scratch потребляется за один шаг, не входит в snapshot/hash и заново
вычисляется после загрузки. Физические позиции принимаются прежней
стабильной серийной фазой; все советы читают начало фазы.

Перед SAT стоит консервативный осевой отсев по сумме полуразмеров обоих
корпусов. Разделённая пара возвращает 0; остальные проходят прежние четыре
оси. Постоянный тест сравнивает ответ с независимым прежним полным SAT.

## Воспроизведение

`bench_crowd --ticks 1800 --workers 1` выполняет пять заездов по 60 секунд
симуляции при 30 Гц. `--legacy-formation` воспроизводит прежнее назначение
мест. `--case convoy --count 64 --ticks 2400` — предел действующего ростера.
`--trace` выводит позиции/цели/recovery каждые 300 тиков.

Сценарии: четыре параллельные колонны; перестроение 10 танков в место клика;
колонна 10 с ведущим вдвое медленнее; встречные пять на пять; слияние через
ворота шириной 12 м. Стартовые корпуса разделены. Тесты дополнительно
проверяют отсутствие пересечений после каждого физического тика.

## Отклонённые эксперименты и остаток

Реактивное руление вправо при встрече уменьшало CPU встречного заезда,
но ухудшало проход ворот. Торможение за любым движущимся соседом также
увеличивало полное время ворот с 2713 до 5185 тиков. Эти варианты не приняты.
Расширение на прямые промежуточные участки тоже отклонено: за первую
минуту ворот доезжали 7 вместо 6, но к 7200 тику оставался один затор
(исходная версия завершала все 10 к 2713 тику).
Ограничение подсказки прямым финальным участком сохраняет исходные хеши
встречного заезда и ворот; это проверяется повторным заездом.

Встречный поток и слияние через узкое место требуют следующего отдельного
шага: локальные очереди/приоритет прохода, сохранение проезда после прибытия,
проверка с 10/32/64 корпусами и смешанными размерами. Сначала измерять
пропускную способность и худшее ожидание, затем допускать изменение.
Нельзя выдавать рост FPS или решение всех заторов на основании открытого
поля. Текущий ростер ограничен 64: поведение и цена для 5000 не доказаны.

## Следующие изменения по приоритету

| Приоритет | Работа | Условие принятия |
|---|---|---|
| P0 | Общий локальный приоритет/очередь при слиянии и встрече, с ограниченным ожиданием | Все 10 проходят быстрее прежних 2713 тиков ворот; встречный поток не хуже; нет новых пересечений/зависаний; replay1/4/8 |
| P1 | Проверить повторное использование статического коридора группы при сохранении индивидуального физического допуска | Меньше frontier work и p99 в воротах/встрече, актуальные правки мира видны сразу |
| P1 при росте числа акторов | Пространственный индекс соседей вместо всех пар | Битовый oracle против текущего полного обхода; стабильные ID контактов; обновление принятых поз; фиксированный потолок |
| P2 | Плотная расстановка смешанных размеров и иерархическое назначение больших групп | Не увеличивать путь/столкновения; не переносить кубический Hungarian на тысячи акторов |

Сначала расширить fixtures до 32/64 для ворот/встречи, смешанных корпусов,
поворота 90°, повторного приказа, остановившегося/разбитого ведущего и
заблокированных конечных мест. Сейчас--count64 проверяет только колонны
и перестроение; смешанный тест проверяет геометрию мест, а не полный заезд.
Живой BlastRange ищет маршруты отдельных акторов: описанное в общей
архитектуре групповое поле направлений не следует считать уже подключённым
к этому пути. Новое поведение проверяется через обычные команды SIM,
сценарии остаются только геометрией, расстановкой и входными приказами.
