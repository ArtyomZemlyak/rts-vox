# Плотность материалов и сохранение уже учтённой материи

Дата: 08.10.2026. Продолжение EP-02a/02b после [224](224-engine-material-commands.md).
Контроль — frozen 224. Приёмка записана до измерений в
`out/engine-fixes-20261008/density-commands/acceptance.json`.

## Причина ошибки

Прямой density setter панели менял Registry, но оставлял прежние количества
в Body, Fuel и Debris containers. Разрушение, плавление и отделение секций
снова вычисляли перевод как число клеток × **текущая** плотность. При большой
плотности перевод упирался в остаток и падал на assert; при малой оставлял
материю в уже разрушенном корпусе. Loader сравнивал сохранённые количества
с новой ценой клетки. Fuel также читал изменяемый Registry: при плотности
1 округление давало нулевой burn, а формула тепла делила на burn. Панель
показывает материалы 1…8, топливо имеет ID9; перенос Density в общий вход
без исправления Fuel открыл бы этот путь для принятой команды ID9.

## Принятая семантика

Плотность меняет свойства ещё не извлечённого грунта. Его количество
раскрывается в ledger только после подтверждённого удаления клетки; claim
сам по себе не создаёт материю. Значение на момент confirmation определяет
количество и массу нового фрагмента. Аннигиляция и горение грунта используют
ту же текущую плотность при раскрытии и списании. Проверка устойчивости
неизвлечённого рельефа также читает текущий Registry.

Уже созданные тела, топливо и обломки сохраняют количество и физическую
массу. Initial Body/Fuel используют исходные плотности фиксированного набора
мира. Они захватываются один раз при создании Matter и восстанавливаются
из того же набора до загрузки состояния. Все переводы из корпуса, плавление,
аннигиляция, отделение root/segment sections и расход топлива используют эту
базу. Масса ходовой по-прежнему определяется chassis data; команда плотности
материала её не перенастраивает.

У обломков уже есть intrinsic mass_g и ledger quantity. При слиянии оба
складываются; средняя плотность может быть дробной (две клетки при 120 и 121
содержат 241). Повторное вычисление количества через текущий Registry
недопустимо. Слияние, пробуждение и реклейм работают с сохранённым количеством.
Команда не обходит обломки или корпуса, не меняет initial ledger и не создаёт
нового стока. Сценарные названия и расстановка не выбирают алгоритм.

Настройка применяется к будущим извлечениям грунта. Панель показывает
это явно. Существующий range adapter по-прежнему учитывает тела
как материал 3; новые произвольные body/fuel stocks потребуют захвата их
собственной базы при создании в рамках будущего lifecycle. Здесь нет такого
создания или скрытого переноса сценарной логики в обработчик команды.

## Команда и сохранение

`MaterialField::Density = 2` дополняет TuneMaterial; старые коды 0/1 и tag4
portable checkpoint не меняются. Ноль нормализуется в 1, Registry отклоняет
значения выше MAX_DENSITY, воздух и отсутствующие ID. Неизменённое значение
даёт Unchanged; отвергнутый/no-op ввод не включает новый формат.

После принятого изменения плотности сохраняется density_history. Snapshot57
использует разреженный material prefix версии 56 с третьим битом density;
пустой список разрешён после reset. История не исчезает при возврате значения:
в мире могут остаться смешанные фрагменты. Прежние flags Blast/motion и хвосты
сохраняются, а исходные snapshots 27…56 читаются без изменения правил.
Миры без density edits сохраняют прежние bytes/hash. Старые executable
не читают snapshot57 и pending Density с новым кодом поля.

В snapshot57 Body и painted body fragments сверяются с исходной плотностью,
Fuel — с исходной ёмкостью. Terrain fragments требуют существующий ненулевой
материал и quantity в диапазоне count…count×MAX_DENSITY. Проверки баланса всего
ledger, caps, живого Kind::Debris, уникального container ID и физической формы
остаются. В старых версиях fragment quantity проверяется точно по Registry.
Это смена модели сохранённого количества с version gate; она не доказывается
одной лишь успешной загрузкой. Физические тесты проверяют реальные переводы,
массу, накопленные стоки и повторное продолжение игры.

## Проверка

Целевой release-прогон `density_` — **10 pass, 0 fail**. Он выполняет
реальные fracture/melt/annihilation, root/leg sections с частичным извлечением,
горение и spill топлива, pending terrain claim, смешивание 120/121,
потерю опоры, посадку и реклейм. 240-тиковый бой меняет плотность несколько
раз и сбрасывает значения, восстанавливая pending runtime и применённое
состояние в ходе боя. Добавлены комбинации material/debris/motion и отказы
для неверных prefix/quantity/material/kind даже при сходящемся ledger.

Первый полный прогон обнаружил ошибку новой тестовой последовательности:
она пыталась reclaim движущейся кучи до посадки. После исправления fixture
куча действительно падает, приземляется и только затем собирается;
проверки массы/количества сохранены на каждом шаге. Лог первого прогона
сохранён отдельно, production-код ради этого теста не менялся.

Полный release-прогон sim-core/nav/modding — **976 pass, 0 fail, 6 ignored**,
из них 53 проверки данных и 923 проверки симуляции/навигации. Blast UI —
**154 pass, 0 fail, 4 ignored**. Все восемь density buttons, числовой ввод,
reset и paused rebuild проверены через общий command ingress. Architecture
сохраняет прежние **5 pass / 4 fail, 46 нормализованных диагностик** без
добавлений: render writes, floats, hash containers, clock. Rustfmt check и
git diff --check проходят. Золотые файлы и зависимости не изменены.

Три последовательных stock боя по 3600 тиков, 60 юнитов, 8 physics /
8 navigation workers: frozen 224, кандидат 225 и кандидат с late restore
3300→3600. Совпали **все 25 нетайминговых полей каждого тика**, shots/damage,
alive [26,21], базы [100,100], peak_rounds=30 и hash **`5dd0c782d2b2f557`**.
Mean step — **13,319 / 13,208 / 13,365 мс** соответственно. Устойчивое
ускорение этот ряд не доказывает. Runtime с изменениями плотности проверен
отдельным 240-тиковым боем; stock прогоны доказывают сохранность прежнего пути.
Нативный допуск объявлен заранее: FPS ≥97% контроля, p99 ≤103%; одна пара
служит проверкой регрессии и не доказывает ускорение.

Одна ordinary пара world-battle по 120 секунд, control → кандидат,
1600×900, AutoNoVsync, 8 physics / 8 navigation / 4 compute workers.
Настройки закрыты, GPU/core trace выключен. Сборка и тесты завершены до
замеров. `--require-valid` и итоговая qualification подтверждают
valid/eligible для обоих запусков и соответствие executable паспортам.
