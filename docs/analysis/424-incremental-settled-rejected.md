# 424 — Incremental `Settled`: отклонено по корректности и цене

1 ноября 2026. Артефакты: `out/optimization-424/`.

## Прототип

Для выбранных кандидатов хранились стабильные ID в `BTreeSet` ячеек.
Прежний и текущий selected-наборы сравнивались по ID, обновлялись только
добавленные/удалённые записи, а `ID→source` восстанавливал контактный индекс.
При несортированных ID предусматривался полный fallback. Полный y-диапазон
выбранного куска заменял прежнее ограничение `want.column`.

После исправления тестового доступа и очистки пустых поколений12/13
`settled`-проверок проходили; оставшийся отказ `zero_room...` существует и на
неизменном baseline. Диагностическая debug-сборка дополнительно подтвердила
совпадение обязательных ячеек с full builder на300 тиках.

## Расхождение поведения

Release A/B показал31 560 различий нетайминговых полей. Первое — на тике259:
`flying`3530→3528, затем изменились фрагменты, валка и дальнейший бой.

Причина установлена: hull может разбудить лежащий фрагмент, который не входил
в исходный `asks/want`. Последующий запрос такого фрагмента может выйти за
старую маску. Полный y-диапазон возвращает контакт, которого прежний индекс
не содержал. Superset ячеек поэтому не эквивалентен: прежняя фильтрация
`want.column` является частью наблюдаемой физики, даже если выглядит как
простое ограничение работы.

BTreeSet, обновления ID и более широкие ячейки также оказались неприемлемо
дорогими. Исправление семантики только поэтому не оправдывает продолжение
этой реализации.

## Решение и требование следующего кандидата

Runtime-прототип не переносится в рабочее дерево. ADR не создаётся. Следующий
incremental-индекс обязан побитово воспроизводить `want.column` и hull-wake
вне исходного `asks`; хранение superset контактов недопустимо. OPT316-04a
остаётся открытым, эта конкретная схема не используется.
