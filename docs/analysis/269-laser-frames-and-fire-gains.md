# Нагрузка после быстрых воронок: лазерный ореол и огонь

Продолжение анализа [268](268-blast-latency-and-row-batching.md),
13.10.2026. Исходный main — `4ffbaa3`; быстрый темп взрывов входит
в тот же набор изменений. Решения общего движка,
без исключений для сценариев и без уменьшения урона/объёма воронок.

## Откуда прибавилось время

Повторный headless A/B, physics4/navigation8/Rayon4, 60 машин,
по два прогона 3600 тиков каждой версии, порядок base/candidate/candidate/base.
Хеш старого темпа `acd46a885be5d219`, нового `c7f2c4f503986ec3`.
Повторы одной версии совпали по всем нетайминговым счётчикам каждого
тика. Между версиями это сравнение разных игровых траекторий:
раннее разрушение меняет урон, маршруты, стрельбу и оседание обломков.

| Фаза | Старый темп, мс/тик | Быстрые воронки до доработки, мс/тик |
|---|---:|---:|
| Весь тик | 11,579 | 13,477 |
| Движение, всего | 4,674 | 3,631 |
| Обломки | 2,391 | 2,778 |
| Карта завалов | 1,835 | 2,283 |
| Огонь, тепло юнитов и дренаж правок | 0,397 | 1,143 |
| Лазер, всего | 0,167 | 0,684 |
| Обвалы | 0,744 | 1,023 |

Лазер входит в обработку приказов: эти строки нельзя суммировать
с общей фазой приказов. В новом конце боя 26 561 обломок вместо
24 301; очередь валки 2 782 777 вместо 2 591 517. Это не доказательство
регрессии точного алгоритма захвата; это фактически выросшая работа.
Однако для игрока она всё равно означает нагрузку, и её нельзя скрывать
за красивым результатом микробенчмарка.

## Точные изменения

Для одного лазерного ореола строятся `HitFrames` ближайших корпусов:
преобразования корпуса/башни/сегментов и их консервативные боксы.
Все образцы и короткие радиальные лучи читают одну неизменную геометрию.
Повторное вычисление преобразования на каждый образец исключается;
порядок корпусов, владение локальным вокселем, щиты, дозы и термические
квоты прежние. Кэш живёт только внутри ореола и не входит в сохранение.
Серийный тестовый эталон оставляет прямой `RangeUnit::hit`.

Для соседних прибавок огня используется существующий `fx::lookup::Lookup`
с фиксированным FxHasher. Его интерфейс запрещает обход в хеш-порядке.
Суммы собираются из прежнего снимка горящих источников; обработанные
прибавки удаляются при прежних условиях. Остаток применяется только
после сортировки координат. Захваченные/уже исчезнувшие клетки,
нулевые суммы, курсор и охлаждение сохраняют прежний смысл.
Тестовый эталон использует прежнее `BTreeMap`. Постоянного кэша нет.
Проверка переполнения сохранена: release проекта работает с
`overflow-checks=true`; замена сложения на wrapping здесь нарушала бы
поведение для больших разрешённых fuel. Добавлены крайние суммы,
присутствующий нулевой ключ и явная проверка переполнения.

## Регулятор полигона

Найден оставшийся максимум UI 8192 при штатных пресетах 65 536/98 304.
При нажатии «+» вычисленное значение ограничивалось сверху и становилось
намного меньше исходного. Исправлены и описание регулятора, и typed setter:
верхняя граница совпадает с уже существующей в `ExplosionConfig::validate`
— 1 048 576. Границы движка и mod-API не расширяются. Проверены реальные
нажатия «+» для всех семи пресетов, typed ввод, команда, snapshot и
пересборка при паузе. Явно сохранённые overrides остаются пользовательскими;
файл настроек не очищается. Это не изменение штатных квот ADR-697.

## Отвергнутый вариант

Все передачи огня складывались в плотный массив, сортировались
и сжимались, затем читались бинарным поиском. Пара 2×3600 тиков
с этим вариантом и кэшем лазера сохранила все счётчики и хеш:
`c7f2c4f503986ec3`. Лазерный ореол снизился 0,606 → 0,548 мс (−9,5%),
но heat_flush вырос 1,126 → 1,169 мс (+3,8%); поздние окна огня
также выросли. Массив удалён, выигрыша обработки огня он не доказал.
Общий тик этой пары 13,335 → 13,239 мс не служит основанием оставить
регрессию отдельной фазы: в него входят и выигрыш лазера, и шум остальных.

## Квалификация

Полный финальный core: 948 passed, 11 ignored. Интеграции: 45 passed,
2 ignored; включая golden, stock snapshot/replay, явную живую волну,
условные правки грунта, полное сохранение, экономику, секторы и рельеф.
CLI600 physics1/4/8 и replay300→600 совпали: `5131bc7be4f874fa`.
Архитектура и ссылки документов: 15 passed; bench-driver: 5 passed.
Формальный `cargo bench --lib --profile release` не содержит измеренных
bench-функций (959 ignored); он не доказательство скорости.

У stock-снимка на 100-м тике теперь может не быть живой волны: он
использует поддерживаемый формат 52. Прежний тест неправомерно требовал
59+, где есть флаг владения конфигурацией. Проверка corrupt flag вынесена
в явный стенд медленной волны возле корпуса, где хранится доля энергии
тела. Для обычного снимка проверяются реальные присутствующие поля;
обёртка 66 учитывается, неподдерживаемый будущий заголовок — 67.
Сохранение и побитовое продолжение штатного боя не ослаблены; снимки
промежуточных волн отдельно проверены явными fixture и быстрым залпом.

Выпускные бинарники с окончательным проверяемым сложением: порядок
before/after/after/before, по два прогона 3600 тиков каждой версии,
одинаковый быстрый темп и конфигурация physics4/navigation8/Rayon4.
Все нетайминговые поля каждого из 14 400 тиков совпали, итоговый хеш
`c7f2c4f503986ec3`. Это сравнение точной оптимизации ADR-698,
в отличие от сравнения разных темпов выше.

## Оконная квалификация и отрицательный результат большого боя

По одной паре на сцену, 120 секунд, 1600×900, AutoNoVsync,
NVIDIA GeForce RTX 5090/Vulkan, physics4/navigation8/Rayon4/Compute4.
Порядок: base-world, base-canister, candidate-world, candidate-canister;
без параллельных сборок, тестов, захвата экрана и phase/task/GPU tracing.
Все четыре записи: ValidForComparison=true, AcceptanceEligible=true,
MeetsSimulationRate=true, 3600 тиков; контекст окна и фокус неизменны.
Хеш каждой версии совпал с её собственным headless-прогоном.

| Сцена и метрика | Исходный main, старый темп | Итоговый код, быстрый темп |
|---|---:|---:|
| world-battle, средний FPS | 94,7 | 77,4 |
| world-battle, p95 / p99 кадра, мс | 24,472 / 29,692 | 26,908 / 36,186 |
| world-battle, максимум кадра, мс | 51,727 | 83,931 |
| world-battle, кадров > 6,06 мс | 5578/11 361 (49,1%) | 6611/9287 (71,2%) |
| canister, средний FPS | 301,6 | 313,7 |
| canister, p95 / p99 кадра, мс | 5,298 / 6,576 | 4,581 / 5,909 |
| canister, максимум кадра, мс | 36,055 | 41,802 |
| canister, кадров > 6,06 мс | 599/36 185 (1,66%) | 273/37 639 (0,73%) |

В большой сцене FPS снизился на 18,3%, p99 вырос на 21,9%; это
**отрицательный результат для игрока**, несмотря на ускорение точных
алгоритмов. Средний core в окне 13,002→14,718 мс. В картечной сцене
направление лучше и p99 проходит 165-FPS бюджет, но максимум хуже;
every-frame цель не пройдена ни одной записью. Одна пара не устанавливает
устойчивую величину выигрыша/регрессии. Темп ADR-697 сохранён ради явно
запрошенных быстрых воронок, а не объявлен общей победой производительности.

Между старым и новым темпом состояния не равны:
world `acd46a885be5d219`→`c7f2c4f503986ec3`,
canister `3969a56055eb0cfd`→`af4132ebfdc05b63`.
45 хешей RON-файлов каталога одинаковы во время оконной пары, однако
старый executable содержит **старые встроенные пресеты**: это не
доказательство равенства всех игровых входов двух сборок. Сравнение
точного ADR-698 при одинаковом состоянии — отдельная пара выше.

Происхождение executable подтверждается замороженными копиями и SHA-256;
GitHead оконного манифеста — каталог запуска, не источник компиляции базы:

- Итог `441cded`, blast: `7714B9ECE4217A1F93D04223CCEBEA5BC2618F7CFBFB5C49334B7F1092191732`.
