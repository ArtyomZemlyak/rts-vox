## MagicaVoxel: редактирование действительно дошло до игры

Источник — тестовый разведчик из 401: размер **36×16×22**, **4302 клетки**.
Открыта отдельная копия в `out/art-lab-403/magicavoxel/`, исходный VOX из 401
сохранён. После правки кистью и сохранения:

- осталось **4300 клеток**, удалены `(16,9,5)` и `(18,9,5)` в системе координат игры;
- размер первого и единственного объёма остался 36×16×22;
- индексы всех оставшихся клеток сохранились;
- все пять используемых цветов совпали побайтно;
- изменился только **неиспользуемый слот палитры 256**:
  `(128,128,128,255)` → `(0,0,0,0)`;
- файл вырос с 18 304 до 42 613 байт: размер контейнера не равен числу клеток.

Результат сохранён как `scout-edited.vox` и повторно открыт самим MagicaVoxel.
Через панель Export выполнен OBJ-экспорт:
`scout-edited.obj`, `scout-edited.mtl`, `scout-edited.png`.
OBJ содержит **324 треугольника**, текстура палитры имеет размер **256×1**.
Это оболочка модели, не замена VOX с внутренними клетками.

Сохранённый VOX помещён в отдельный тестовый pack с прежним соответствием
индексов Armour/Core/Engine/Weapon/Sensor. Уже собранный в 401 проверочный
инструмент, связанный с настоящими `modding::vox` и `UnitBody`, подтвердил:

```text
4300 cells; all subsystems connected; engine/core removal PASS
```

То есть редактирование, импорт, связь с ядром и проверки удаления двигателя/
ядра прошли. Это проверка тестовой модели, не всех возможных проектов MagicaVoxel.
Иерархия из нескольких моделей и переносы scene nodes по-прежнему требуют
отдельного flatten/контроля: загрузчик игры использует первый объём.

Для читаемости интерфейса на 4K временно изменялся `ui_scale` portable-копии.
Её исходный `config.txt` восстановлен; копия сохранена рядом с результатами.

## Нативный VoxEdit: точные операции работают, изображение не подтверждено

Ошибки веб-сборок из 402 не переносились на настольную версию. Запущен
настоящий `vengi-voxedit.exe`, загружен наш VOX; лог подтвердил один model node.
Для операций использован официальный канал команд:

```text
\\.\pipe\vengi-voxedit-input
```

Передача команд через `NamedPipeClientStream` ограничивалась таймаутом
подключения 1500 мс. Это API самого редактора, не отдельный запуск voxconvert
и не имитация редактирования выходного файла.

Проверенные операции:

1. `save` → `scout-roundtrip.vox`: размер, все **4302 клетки**, их индексы
   и используемая палитра совпали с исходником.
2. `rotate y` → `scout-rotate90.vox`: размер **22×16×36**, 4302 клетки;
   подтверждено преобразование `(x,y,z) → (z,y,35-x)` вместе с индексами.
3. `rotate y 3` → `scout-rotate360.vox`: исходные координаты и индексы
   восстановились точно.
4. `save` → `scout-editor.glb`: **1 mesh, 3 primitives, 244 треугольника**.
5. Сохранённый VOX загружен вторым запуском редактора.
6. Проверка pack настоящим импортёром игры: **4302 клетки**, связь подсистем
   и удаление двигателя/ядра прошли.

Визуальную часть нельзя считать успешной. Захват Windows Computer Use
завершался `FrameArrived timed out: timed out waiting on channel` после
повторной попытки. Штатная команда `screenshot` создала `viewport.png`, но
изображение оказалось чёрным. Причина не установлена: исправный экспорт не
доказывает исправный viewport, а сбой захвата не доказывает поломку геометрии.
Оценка удобства кистей/камеры native VoxEdit остаётся открытой.

## Blockbench desktop: сохранение и экспорт проверены отдельно от web

Настольный Blockbench открыл `probe-input.bbmodel` из 401 и показал меш.
Через меню сохранён `probe-desktop.bbmodel`. В панели Transform положение X
изменено **0 → 1**, проект сохранён штатным действием Save Project.

Разбор сохранённого JSON подтвердил:

- один меш, восемь вершин;
- локальные вершины и грани совпали с исходными;
- `origin` изменился `[0,0,0] → [1,0,0]`.

Через File → Export → glTF выбраны **Binary (glb)** и масштаб экспорта **16**.
Создан `probe-desktop.glb` размером **2044 байта**. В нём один mesh/primitive,
**12 треугольников**, перенос узла `[0.0625,0,0]`: смещение проекта 1 / 16.
Это подтверждает, что изменение дошло до экспортированного файла.

Геометрия пригодна для обмена с другими 3D-инструментами. Сама по себе такая
оболочка не кодирует внутренние воксели и роли разрушаемого юнита; ограничение
из 401 остаётся. Смещение/масштаб экспорта нужно согласовывать отдельно.

## Effekseer Recorder: настоящий экспорт, обнаружена обрезка

В GUI открыт `edited-project.efkefc` из 402. В дереве показаны пять узлов
`RTS_Lab_0` — `RTS_Lab_4`, в viewport виден эффект. Это производная тестовая
копия поставляемого Laser-примера, **не пример нужного кубического стиля**.

Recorder проверен со следующими параметрами:

```text
Width / Height: 256 / 256
Scale: 1
Start / End Frame: 1 / 30
Frequency: 1
Export as a single image
X Count: 4
Make transparent: Generate alpha
```

В интерфейсе изначально была слишком маленькая floating-панель. В сохранённой
раскладке portable-редактора Recorder увеличен с 300×300 до 1800×1500 физических
пикселей. Исходная раскладка лежит в `effekseer/layout-original.ini`.
Увеличенная панель оставлена для удобства дальнейшего использования на 4K.

Создан `recorder-atlas.png`: **1024×2048**, раскладка **4×8**, 30 кадров
и две пустые ячейки. FFmpeg действительно декодировал PNG в RGBA:

- все **30 кадров непустые и различаются** по декодированным пикселям;
- присутствует частичная альфа и прозрачный фон в части кадров;
- обе неиспользованные ячейки полностью прозрачны;
- эффект касается края **во всех 30 кадрах**, в поздних кадрах заполняет
  практически весь квадрат: требуется более широкая область кадрирования.

Первоначальное предположение «каждый кадр обязан иметь нулевую альфу» оказалось
неверным: растущий эффект может заполнять кадр. Проверка отделяет корректность
RGBA от качества кадрирования и явно сообщает касание края. Обрезанный атлас
не объявляется готовым ассетом.

Повторный запуск для настройки камеры дважды не дал захватить окно:
`FrameArrived timed out`. Процесс закрыт, исправленное кадрирование не заявляется.
Остаётся проверить именно более широкий кадр и нужный режим смешивания на
реальном игровом фоне. [Официальная справка Recorder](https://effekseer.github.io/Help_Tool/en/ToolReference/record.html)
описывает разные варианты альфы для blend/additive; один выбранный режим не
гарантирует одинаковую передачу обоих типов частиц.

Этот тест проверяет GUI/runtime и Recorder Effekseer, в отличие от GIF из 402,
который был создан Blender. Встроенный runtime в игру не добавлялся.

## Практический выбор

- **MagicaVoxel** — подтверждённый дополнительный редактор разрушаемых
  воксельных моделей. После сохранения нужен контроль первого объёма и палитры.
- **Blender** — основной универсальный инструмент для моделей и подготовки
  эффектов; точный экспорт кубоидов и атласы проверены в 401–402.
- **Blockbench** — быстрый инструмент для форм и простого моделирования;
  desktop-сохранение и экспорт теперь проверены. Для разрушаемости нужен
  отдельный путь подготовки внутренних клеток/ролей.
- **Vengi** — полезен для точного обмена и автоматизации; операции native
  редактора проверены, качество работы его viewport пока не подтверждено.
- **Effekseer** — редактор и запись эффектов работают; интеграция форматов,
  кадрирование и blend/additive требуют отдельной доводки. Подключать его
  runtime только ради проверки инструментов не требуется.
