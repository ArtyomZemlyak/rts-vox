# Членство запросов опор и параллельные строки завалов — 15.10.2026

Исходный `main` и свежий `origin/main` совпадали на `b0784eb`.
Контроль включает [288](288-rubble-support-scratch.md): пустые буферы
опор переиспользуются, результат полностью пересчитывается на каждом
вызове. Исследуется следующий участок общего `Bursts::rubble`, без
изменения сценариев, физических контактов, баланса и квот.

Внедрены точная маска получателей запросов и независимые строки колонок,
ADR-713. Контролируемый Windows ABBA с одинаковыми наблюдателями даёт
карту завалов **−5,85%** в среднем / **−5,49%** поздно, весь тик
**−1,09% / −1,66%**. Это небольшой выигрыш CPU симуляции; native FPS
парой не измерен. Сравнение исходного и нового бинарников bench также
содержит изменение самого стенда и не показало ускорения всего тика;
оба результата и ограничения приведены ниже.

## Диагностика до изменения

Обычный headless bench измерял всю карту завалов, но не её внутренние
родительские этапы. Добавлен отдельный `--profile-rubble`: он подключает
существующий physics observer через `step_observed_all_tasks`, измеряет
восемь родительских spans и выводит среднее в наносекундах на тик за окна
до 300 тиков вместе с числом вызовов. Часы и Mutex находятся только в
бинарнике бенчмарка; игровой SIM их не содержит. Навигационный
`--profile-workers` сохраняет отдельный observer.

Это **inclusive wall time**, включая dispatch/join и вложенные callbacks,
а не CPU отдельных workers. `columns` содержит gather и merge: строки
нельзя складывать как независимые работы. Диагностика добавляет стоимость
наблюдения и не используется для оценки обычного FPS/приёмки 30 Гц.
Обычные сравнительные прогоны выполняются без этого флага.

World7200 AI-vs-AI, physics4/navigation8/Rayon4. В позднем окне
6601–7200 исходный диагностический запуск показывает:

Поэтому параллелизация запросов опор не выбрана первым шагом: их

бинарный поиск source index в отсортированном `stacked` для каждого
фрагмента. Входные indices уже плотные и ограничены fragment slice.

## Проверяемая замена

`RubbleScratch` получает transient `Vec<u64>`: один бит на source index.
Перед каждым непустым support build маска заполняется нулями и получает
ровно indices нынешнего `stacked`. `Settled::around_bounds_into` читает
бит вместо бинарного поиска. Построение маски включено в parent build,
очистка — в parent cleanup; работа не перенесена за пределы измерения.

Маска определяет, какие фрагменты запрашивают опору. Геометрические
маски запросов SettledQueries и состав достижимых опор сохраняются.

Source indices, порядок запросов, клетки, высоты и выбор опоры прежние.
Маска очищается после использования; пустой вход также не видит старых
битов. Capacity переиспользуется, как остальные буферы 288. Дополнительное
хранилище имеет длину `ceil(fragments/64)` слов и удерживает достигнутую
ёмкость до удаления сцены. Экономия RSS не заявляется. Маски и буферы
не входят в save/hash; публичный immutable rubble API сохраняется.

Oracle проверяет границы 63/64/65, 127/128/129, 1023/1024/1025,
смену resting-membership без смены тика, копку и движение корпусов,
yielding, пустые входы и повторное использование памяти. Отдельный тест
диагностики проверяет вложенные parent spans, исключение других стадий
и leaf-событий, сброс окна.

## Независимые строки колонок

Опыт только с маской дал слишком малый суммарный эффект, поэтому
проверяется также более дорогой merge. После прежнего scatter по X
каждая полная строка независимо вычисляет точные максимумы по Z.
Большой плотный вход с не менее 16 384 записями и диапазоном X
не менее 512 индексируемых строк, включая пустые,
в многопоточном пуле обрабатывается indexed-пачками по 64 строки.
Малый/узкий вход и один поток сохраняют последовательный путь;
разреженные карты сохраняют прежний sort/dedup fallback.

Внутри строки максимум скалярный; параллельной редукции нет. Пачки
собираются и конкатенируются в порядке X, внутри каждой строки Z
выдаётся по возрастанию битов. Высота ноль сохраняет присутствие,
верх u16::MAX обрабатывается прежним u32 sentinel top+1. Передача
неизменяемых rows и starts исключает зависимость от порядка workers.

`physics_rubble_merge` включает scatter, dispatch, join, копирование
выхода и освобождение временных групп. Добавлены leaf spans
`physics_rubble_merge_rows` для worker-выполнения, включая пустые пачки.
Opt-in parent-диагностика не суммирует их повторно; native task observer
может показывать workers отдельно.

Цена: суммарная capacity выходных пачек ограничена числом входных
записей (до дополнительных 12 байт/запись для данного tuple layout),
плюс локальные таблицы высот и presence на одновременно работающие
пачки. Родительский Vec сохраняет свою capacity. Экономия RAM не
заявляется, аллокации и join учитываются в полном времени merge.
Полностью пустые пачки не выделяют таблиц высот.

Отдельный oracle сравнивает с BTreeMap при 16 383/16 384/16 385/65 536
входных записях и ширине 511/512/513/1025 на 1/2/4/8 workers,
проверяет число/баланс leaf spans. Прежние проверки покрывают
16-битные края координат, большие дубликаты и идемпотентность.

### Цена изменения стенда и отклонённые оценки

Первый вариант подключения проверял Option на каждом physics event.
В финальной версии выбор вынесен перед тиком; обычный путь снова вызывает
`step_observed_tasks` с пустым физическим observer. Часы и Mutex новой
диагностики при этом не вызываются. Смена кода/специализаций стенда всё
равно может менять размещение/оптимизацию бинарника; внешние причины
разброса тоже отдельно не изолированы.

Маска без строк дала rubble −1,93% / −1,67% поздно; весь тик +0,35%
в среднем и −0,01% поздно. Поэтому она не объявлена достаточной общей
оптимизацией. Объединённый вариант при прямом сравнении со старым
бинарником main дал rubble −5,99% / −6,09%, но весь тик **+0,26% /
+0,63%**. Этот результат сохранён, не заменён выгодным сравнением.
Контролируемый ABBA выше отделяет общий код наблюдателей от изменения
алгоритма. Большой выигрыш всей игры/FPS не установлен.

Raw/frozen — `out/rubble-columns-20261015/`: root хранит первый вариант
observer; `final/` — опыт только с маской; `accepted/` — объединённый
вариант против исходного бинарника; `controlled/` — одинаковый стенд.
В каждом timing-наборе сохранены CSV, логи, script/aggregate/comparison.
Повторная контрольная сборка: `build-control-safe.ps1` с новым пустым
выходным каталогом; он сохраняет/восстанавливает source bytes в finally.
