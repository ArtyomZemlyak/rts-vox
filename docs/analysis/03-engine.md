# Движок: что даёт, чего не даёт, цикл итерации

Проверка ADR-002 и ADR-009 фактами, плюс отдельная тема, которую я до сих пор
недооценивал: **скорость цикла «правка → сигнал»** как инженерное требование.

---

## Что Bevy 0.19 реально даёт

Проверялось именно под наш профиль — много статичных чанков плюс тысячи
движущихся инстансов.

- **GPU-driven рендер.** Группировка multi-draw-indirect батчей перенесена с
  CPU на GPU: на сцене в миллион кубов экономит почти 1.5 мс. MDI и MDIC,
  mesh allocator.
- **Разреженная загрузка uniform-буферов мешей** — грузятся только
  изменившиеся трансформы. Прямо про нас: чанки стоят, юниты движутся.
- **Meshlets / virtual geometry** с 0.14, поверх two-pass HZB — то есть
  Nanite-подобный отбор уже есть в движке, а не надо писать. Уточнение:
  реализован он **не на mesh-шейдерах**, а софтверной растеризацией в compute,
  как в Nanite.
- **Render Graph as Systems (0.19).** API `RenderGraph` **удалён**: проходы
  рендера — обычные системы в расписаниях `Core3d`/`Core2d`, а `RenderContext`
  отдаёт сырой `wgpu` command encoder. Это прямо про нас: кастомный проход стал
  пятистрочной системой.
- **Аппаратный ray tracing достижим уже сегодня.** `EXPERIMENTAL_RAY_QUERY` на
  Vulkan, DX12 и Metal, включается по умолчанию, штатный крейт `bevy_solari`
  его уже использует. Ограничение — процедурная AABB-геометрия требует
  wgpu 30, а 0.19.1 сидит на 29. Детали и цифры — ADR-011, ступень 4.
- **Mesh-шейдеры доступны на пине 0.19.1** через сырой wgpu (приехали в
  wgpu 28). В 0.20 становятся первоклассными. Детали — ADR-011, ступень 2.
- **Профилирование Tracy** через фичу `trace_tracy`, включая отдельную строку
  GPU-спанов. Без него бюджеты из `../10-budgets.md` непроверяемы.
- Render graph, ассеты, окно, ввод, планировщик кадра.

## Чего Bevy не даёт

Честный противовес, чтобы решение не выглядело фанатским.

- **Нет редактора.** Прототип в разработке, для продакшн-пайплайна контента
  не готов. Для проектов с ручным левел-дизайном это, по консенсусу,
  «настоящая проблема, а не мелкое неудобство».
- **Ломающие изменения каждый минорный релиз**, каждый со своим migration
  guide.
- **Тонкая экосистема ассетов**, мало готовых плагинов продакшн-качества.
- **3D-рендер без глубины Lumen/Nanite.**

**Почему нам это почти не мешает.** Три из четырёх пунктов бьют по проектам с
ручным контентом. У нас контент процедурный, баланс в RON, уровней-в-редакторе
нет вообще (`../01-concept.md`, не-цели). Отсутствие редактора — главная слабость
Bevy — для этого проекта не стоит ничего. Это редкое совпадение, и именно оно
делает выбор оправданным, а не смелым.

Остаётся API-drift (R2), который уже учтён и от которого защищает ADR-003.

## Прецедент: Tiny Glade

Первая коммерчески успешная игра на Bevy. Их схема: **Bevy ECS как основа
игровой логики плюс собственный рендер на Vulkan/ash.**

Разработчики описывают ECS как «способ определять игровые объекты и то, как
они работают, в сущности кровеносная система всего происходящего в игре».
Рендер Bevy они заменили, потому что «их потребности переросли то, что Bevy
мог дать на тот момент» — конкретно, нужны были compute-шейдеры для
процедурной генерации на GPU, а Bevy их тогда не поддерживал.

Три вывода:

1. **Схема «bevy_ecs как библиотека + свой рендер» шипнута.** Это не
   теоретическая возможность, а рабочий путь коммерческого проекта.
2. **Их причина ухода сегодня неактуальна** — compute-шейдеры в Bevy есть.
   То есть планка, на которой они соскочили, поднялась.
3. **Их путь — это наш триггер пересмотра ADR-002**, только пройденный до
   конца. Если рендер упрётся, мы делаем ровно то же и сохраняем каркас.

Отличие от нас — в том, какую половину они оставили Bevy. У них ECS держит
игровую логику. У нас логика в SoA, а ECS отдан рендеру (ADR-009), потому что
им не нужен детерминизм, а нам нужен.

## Проверка ADR-009: сколько стоит детерминированный bevy_ecs

Я решил не использовать ECS в симуляции по соображениям, которые стоило
проверить. Факты:

- системы в Bevy **по умолчанию идут в недетерминированном порядке**;
- однопоточный executor это чинит — но ценой отказа от параллелизма, ради
  которого ECS и берут;
- и даже после этого **порядок обхода сущностей в `Query` остаётся источником
  недетерминизма**: в мультиплеерном контексте каждый запрос нужно сортировать
  по стабильному ключу.

То есть детерминированный bevy_ecs = однопоточное расписание плюс сортировка
на каждый запрос. Это дороже, чем плотные SoA-массивы с обходом по индексу,
и при этом отдаёт ровно то преимущество, ради которого ECS брали.

ADR-009 остаётся. Архитектурная разница подтверждена, а не угадана.

## Цикл итерации — то, что я недооценивал

Для агентной разработки время от правки до сигнала важнее почти всего
остального: агент делает десятки итераций там, где человек сделал бы одну.
Rust здесь худший из возможных языков, и с этим надо работать явно.

**Базовые цифры.** Холодная сборка Bevy — 3–7 минут даже на быстрой машине.
Инкрементальная — 10–40 секунд, на мелких правках может падать до 2–4 секунд.

**Рычаги, по убыванию эффекта:**

- **`dynamic_linking`** — самый большой выигрыш: Bevy собирается в динамическую
  библиотеку и не релинкуется при каждой пересборке.
- **Cranelift-бэкенд** — примерно на 30% быстрее компилирует, суммарно до ~50%
  сокращения времени.
- **`lld` / `mold`** — ускоряют именно релинковку, то есть повторные сборки.
- **Hot-patching.** `subsecond` патчит работающий процесс, перехватывая фазу
  линковки и сравнивая ассемблер между сборками; заявленные времена патча — от
  ~130 мс, и интеграция с Bevy встроена, то есть оборачивать функции вручную
  не нужно. Для Bevy также существует `dexterous_developer` с явным объявлением
  перезагружаемых областей.

**Две ловушки, которые сэкономят день:**

- **`dynamic_linking` полностью ломается на Cranelift.** Выбрать можно только
  один из двух.
- **Cranelift ломает инспекцию переменных в LLDB** — то есть отладчик
  становится хуже ровно тогда, когда сборка быстрее.
- **Release-профиль убивает инкрементальность.** Держать dev-профиль для
  итерации, release — только для бенчмарков и golden-хешей.

Отсюда ADR-012.

## Профилирование

Tracy через `trace_tracy`, GPU-спаны отдельной строкой. Ставится на этапе 0
вместе со скелетными бенчмарками: бюджеты из `../10-budgets.md` без профайлера
проверить нечем, а «оптимизировать до бенчмарка» запрещено (`CLAUDE.md`).

## Что осталось непроверенным

- Реальные времена сборки **на этой машине** с 8 доступными ядрами.
  Компиляция Rust параллелится по crate-графу, так что R6 бьёт и сюда.
  Мерить на этапе 0 вместе с остальными бенчмарками.
- Стоимость `Fx`-арифметики (i64×i64 через i128) относительно float на
  реальной нагрузке — см. `04-optimization.md`, раздел 5.
