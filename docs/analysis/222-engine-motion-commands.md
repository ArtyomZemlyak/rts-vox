# Изменение ходовой через общий командный вход

Дата: 08.10.2026. Продолжение EP-02a/02b после
[221](221-engine-settings-read-model.md), контрольная сборка — frozen 221.

## Исправленные причины

`knobs::apply` сам обходил юнитов и менял скорость, шаг и 16 параметров
шасси. Такой writer мешал выделению общего владельца симуляции: настройки
обходили командный вход, результаты исполнения и переносимую очередь.
Кроме того, `Motion::save` не сохранял эти изменяемые поля. После загрузки
они возвращались к исходным значениям, а физический hash не различал
разную настройку ещё не продвинувшегося мира.

Добавлена общая целочисленная `Command::TuneMotion`: вид юнита, отдельный
флаг включения орудия, типизированное поле и значение. `execute_command`
применяет её синхронно; прежний `execute_battle_command` оставлен совместимым
входом. Результат — Applied, Unchanged или Rejected при отсутствии адресатов.
Capture записывает один результат BetweenTicks. `CommandRuntime` исполняет
эту же операцию через существующие epoch/sequence, назначенный тик и бюджет.
Новых сценарных обработчиков и привязок к карте нет.

Семантика прежнего редактора сохранена: обновляются все слоты указанного
вида, обе стороны и погибшие юниты. Орудие — отдельный явный адресат,
независимый от своего вида. Speed ограничивается снизу единицей, Step —
диапазоном 1…8; остальные целые поля сохраняют прежнее присваивание.
UI оставляет свои диапазоны и преобразование введённого числа. Это не
новая полная валидация произвольных физических коэффициентов.

## Сохранение и совместимость

При построении мира один раз запоминаются исходные 18 значений каждого
слота и орудия после применения layout/course. Snapshot сравнивает с ними
текущие поля. Неизменённый мир использует прежнюю версию и прежние байты.
Только при наличии отличий выбирается physical snapshot **54**: существующие
tails записываются полностью, затем добавляется разреженный хвост ходовой.

Формат хвоста: u32 count; для каждого изменённого слота — u32 ID,
непустая 18-битная u32 mask, затем i32 значений по возрастанию номера поля.
Слоты идут строго по возрастанию; ID `units.len()` обозначает орудие.
Пустой хвост, дубли/неизвестные ID, неизвестные биты, значения, равные
исходным, и обрезанные записи отклоняются. После восстановления полей
следующие шаги используют сохранённые параметры. Версии 27…53 читаются
прежним путём; старые executable не читают новый snapshot 54.

Portable checkpoint v1 использует новый command tag 2: kind в прежнем
u64 адресном префиксе, bool include_gun, u8 field, i32 value. Старые tags 0/1
и их байты не меняются; старый reader отвергает неизвестную команду.
Неизвестные kind/field и неканонический bool отклоняются. Runtime hash
включает как очередь с аргументами, так и уже применённые физические значения.

Тик не сканирует defaults и не сериализует мир. Command выполняет один
линейный обход ростера без выделения памяти. Snapshot/hash добавляют
сравнение 18 целых на слот. Defaults требуют 72 bytes на слот плюс Vec;
для 60 юнитов и орудия это 4392 bytes полезных данных без overhead аллокатора.
Полная стоимость snapshot остаётся зависимой от физического состояния мира.

## Сброс на паузе

Прежняя проверка `tick < last_tick` пропускала пересборку 0→0. Overrides
теперь отслеживает generation мира и повторяет сохранённые настройки
один раз после его смены, до следующего физического шага. Проверка отката
тика оставлена для прежних путей восстановления. Первый кадр не дублирует
загрузку настроек. Изображение и параметры обломков/материалов используют
прежние writers; их миграция не объявляется завершённой.

## Приёмка и измерения

До замеров записан `out/engine-fixes-20261008/motion-commands/acceptance.json`.
Проверяются все поля и прежние групповые изменения; восстановление применённых
и ожидающих команд в настоящем бою; строгий разбор форматов; кнопки, ввод,
сброс и пересборка 0→0. Полный stock бой должен сохранить все 25 нетайминговых
потиковых полей frozen 221, итог и hash; late replay — пройти 3300→3600.
Три ordinary native пары по 120 секунд: медиана FPS не ниже 97% контроля,
медиана p99 не выше 103%, valid/eligible и прежний темп симуляции.
Сборки, тесты и тяжёлый анализ не совмещаются с измерениями.

Полный `cargo test --release --locked --offline -p sim-core -p nav`:
**900 passed, 0 failed, 6 ignored**. Шесть новых проверок покрывают все
18 полей, независимое воспроизведение старого setter, обратимость к stock
bytes, результаты исполнения и однократный capture, ошибки snapshot tail
и command wire, участие pending значения в hash. В двух боях по 240 тиков
(Tank и Strider) сравниваются legacy setter, CommandRuntime и replica после
portable restore: сначала со всеми pending inputs, затем после тиков
25, 71 и 151. На каждом шаге совпадают snapshot/hash, в конце — receipts;
оба боя обязаны дать реальные выстрелы и повреждения.

`cargo test --release --locked --offline -p render --bin blast`:
**148 passed, 0 failed, 4 ignored**. Три новые проверки проходят 18 кнопок
каждой из двух групп и проверяют ровно одну typed command на нажатие;
проверяют возврат исходных параметров, clamped числовой ввод и однократное
повторение overrides после generation change при tick0→0.

Architecture: **5 passed, 4 известных failed**, **46→46** нормализованных
диагностик, новых и исчезнувших нет. Остаются прямые render writers,
floating point, hash containers и часы в проверяемых путях. Проверка не
обнаруживает все записи через промежуточные mutable ссылки, поэтому
неизменное количество сообщений не означает отсутствия продвижения границы.
`rustfmt --check` и `git diff --check` проходят.

Три последовательных полных headless запуска по 3600 тиков, 60 юнитов,
8 physics / 8 navigation workers: frozen 221 control, кандидат, кандидат
с восстановлением 3300→3600. Во всех совпали **25 нетайминговых полей
каждого тика**, shots/damage, alive [26,21], базы [100,100], peak_rounds=30
и hash **`5dd0c782d2b2f557`**. Позднее восстановление прошло. Mean step:
**13,234 / 13,249 / 13,378 мс** соответственно. Это проверка корректности
и регрессии stock пути, не доказательство ускорения; изменённые параметры
и ожидающая очередь проверены отдельно в двух 240-тиковых боях выше.

## Оставшаяся работа

Это законченный командный путь ходовой, а не весь EP-02/03. Далее нужны
остальные product writers: параметры обломков, материалы, конфигурация
оружия, lifecycle/setup. Для каждого надо проверить не только pending
checkpoint, но и сохранение уже применённого состояния — найденная здесь
потеря полей показала, почему одной сериализации команды недостаточно.
В текущем `Matter::save` параметры Blast и реестр материалов отсутствуют;
`Matter::load` передаёт текущий tuning в `Bursts::load_material` и вычисляет
по нему предел ledger. Поэтому эти настройки требуется восстановить **до**
валидации зависимого физического состояния, а не просто дописать в последний
хвост и применить после загрузки. Конфигурация оружия пока передаётся
отдельным аргументом `BlastRange::restore`; её командная миграция должна
явно определить владение конфигурацией в checkpoint.
Затем полный geometry/terrain export и перенос владельца из кадрового цикла.
Capacity/progress, исторические обходы и цель 165 FPS остаются самостоятельными
частями [плана](200-engine-performance-plan.md). Ускорение окна от переноса
редких настроек в команду не предполагается.
