# rts-vox — рабочие правила

Воксельная RTS, полностью разрушаемый мир, **ресурсы добываются копкой**,
5000+ юнитов, детерминированная симуляция. Rust. Стадия: тех-концепт, кода
ещё нет.

Копка это экономика, а не спецэффект: изменение мира идёт каждый тик от сотен
юнитов. Отсюда потолок `MAX_VOXEL_EDITS_PER_TICK` с очередью, навигация по
проходимым вокселям вместо heightmap и постоянная, а не событийная нагрузка
на ремешинг. См. `docs/14-mining-and-terrain.md`.

Детали — в `docs/`. Здесь только то, что нарушать нельзя.

## Инварианты

**Детерминизм симуляции.** В `sim-core` и всех крейтах, от которых он зависит:
- Никаких `f32`/`f64`. Только тип `Fx` (i64, Q32.32) из `sim-core::fx`.
  Исключение — только рендер-слой, где расхождения безопасны.
- Никакого `HashMap`/`HashSet` в итерируемых путях. `BTreeMap`/`BTreeSet` либо
  плотные массивы с индексами. Порядок итерации обязан быть стабильным.
- Никакого `std::time`, `rand::thread_rng`, I/O, глобального состояния.
  RNG только `sim-core::rng` с явным сидом.
- Порядок систем в тике фиксирован явным списком, а не расписанием фреймворка.

**Границы слоёв.** `sim-core` не знает про Bevy, wgpu, окна, ассеты и файлы.
Он получает вход (сид, команды) и отдаёт состояние. Рендер читает состояние —
никогда не пишет в него. Нарушение этой границы = откат.

**Данные, не код.** Любое игровое число (стоимость, HP, урон, скорость,
прочность материала, тайминг) живёт в `data/*.ron`, а не в исходнике.
Хардкод числа баланса в `.rs` = ошибка.

**Пины версий.** Версии в `Cargo.toml` пинятся точно (`=0.19.1`).
Не обновлять зависимости без явной просьбы. Проверенный список версий —
`docs/10-verified-facts.md`.

## Антипаттерны

- Класть игровое состояние в рендер-компоненты.
- Использовать Bevy ECS для симуляции (ECS — только рендер, см. ADR-009).
- Добавлять зависимость, не обсудив.
- Оптимизировать до бенчмарка. Сначала измерение, потом оптимизация.
- Расширять vertical slice. Всё за пределами текущего этапа `docs/09-roadmap.md`
  не делается, даже если «займёт пять минут».

## Bevy: как не галлюцинировать API

Bevy ломает API каждые 3.5–5 месяцев, и обучающий корпус модели отстаёт.
Перед тем как писать код под незнакомый Bevy API:
1. Прочитать исходник из `~/.cargo/registry/src/*/bevy-0.19.1/`.
2. Или посмотреть примеры в `examples/` того же каталога.
3. `cargo build` — единственный источник истины. Не «выглядит правильно».

Если API из головы не компилируется дважды подряд — читай исходник, не угадывай.

## Проверка работы

Порядок обязателен: тесты **до** рендера. Ни одна подсистема не считается
готовой, пока не проходит headless из терминала.

```
cargo test                      # включая golden/property/replay
cargo bench                     # пороги в docs/06-simulation.md — регрессия = провал
cargo run -p sim-cli -- --seed 42 --ticks 1000 --dump-hash
```

Типы тестов и что они ловят — `docs/04-determinism.md`.

## Что делать при неопределённости

Спрашивать, а не выбирать за меня, если решение:
- меняет границу слоёв или контракт мод-API;
- добавляет зависимость;
- меняет формат сохранённых golden-файлов;
- касается пункта, помеченного в `docs/` как «открытый вопрос».

В остальном — решай сам и фиксируй решение в `docs/02-decisions.md` новым ADR.
